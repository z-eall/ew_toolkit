# pid/Ownership Code-Proof Ledger

Code-proof side of the pid/ownership mechanic. Cross-reference: `EWP_pid_behavior.md` (maintainer's own hand-tested, empirical side — kept separate, not merged). Method: `.scratch/ew-wiki-player-identity/spec-pid-ownership-mechanic.md` (Tier A/B/C test, both-chains rule, Effect-chain rule).

Decompile source: `valheim-modding/decompiled/1.0.12_2026-09-11/assembly_valheim/` (newest dated folder at time of this sweep; `1.0.7_2026-09-10` also exists but is older).

**Mechanical baseline** (per spec §3): only three things ever change a ZDO's owner — the universal creation-time call (`ZNetView.Awake → ZDOMan.CreateNewZDO → SetOwnerInternal(m_sessionID)`, every object, unconditional), the universal periodic sweep (`ZDOMan.ReleaseZDOS`), or an explicit `SetOwner(`/`SetOwnerInternal(`/`ClaimOwnership()` call inside a specific component. This sweep found every component-level call site by grepping the *entire* decompiled tree (`\.SetOwner\(`, `\.ClaimOwnership\(`, `SetOwnerInternal\(`) rather than sampling files from the behavior table, then added every hit not already in the maintainer's checklist.

**Full-tree grep results** (both forms; core ZDO/ZDOMan/ZNetView/ZNetScene infrastructure files excluded from this list since they implement the universal mechanism itself, not a component):

- `.SetOwner(` hits: `Vagon.cs`, `Ship.cs`, `ItemStand.cs`, `Trap.cs`, `Container.cs`, `TeleportWorld.cs`, `ArmorStand.cs`, `Game.cs`, `ItemDrop.cs`, `Sadle.cs`
- `.ClaimOwnership(` hits: `Player.cs`, `Turret.cs`, `CookingStation.cs`, `TerrainModifier.cs`, `Fish.cs`, `TimedDestruction.cs`, `Container.cs`, `Sign.cs`, `Fireplace.cs`, `Pickable.cs`, `Gibber.cs`, `StatusEffect.cs`, `SE_Demister.cs`

Plus the maintainer's own checklist components that show **zero** hits either way (each re-verified fresh in this sweep): `Beehive.cs`, `Piece.cs`, `WearNTear.cs`, `Feast.cs`, `Character.cs`, `Ragdoll.cs`, `Tameable.cs`, `Smelter.cs`, `MineRock.cs`/`MineRock5.cs` ("Rock Frac"), `BossStone.cs`/`OfferingBowl.cs` ("Boss Altar"), `SiegeMachine.cs`, `EffectList.cs`, most of `Player.cs` (one unrelated hit found — see row below).

**`prefab:` value-group addendum (ticket 07, object-ownership.mdx review pass, 2026-09-15)**: confirmed directly in EWP's own `docs/scripting.md` — "By default, each object component has its own value group. For example `Tameable` or `Piece`." This means `prefab: Container`/`prefab: Trap`/etc. is real, documented EWP syntax: it matches *every* object carrying that component, not one specific prefab id. This was initially (wrongly) rejected as invented syntax during this same review pass, based on this wiki's own beginner docs never mentioning it — corrected after checking EWP's real source/docs directly rather than trusting this wiki's own silence on the feature. Worth using in future object-appendix entries (tickets 08-12) where a component has many real prefab variants, instead of picking one example id and saying "swap in your own."

**Field-name addendum (ticket 07, object-ownership.mdx review pass, 2026-09-15)**: the wiki page had invented literal EWP field names for both ItemStand and ArmorStand that don't match the actual ZDO keys — caught by re-deriving them from the decompile directly rather than trusting the page's prior text. Confirmed:
- **ItemStand** writes the mounted item's hash to `ZDOVars.s_item` (`ItemStand.cs`), which hashes the literal string `"item"` (`ZDOVars.cs:141`) — the EWP-visible field name is `item`, not `_item` as the page previously said.
- **ArmorStand** writes each slot's item hash to a per-slot key built as `(i + "_item").GetStableHashCode()` (`ArmorStand.cs:356-366`, called with `"_item"` at line 353) — for C#, `int + string` is string concatenation, so slot 0's real field name is `0_item`, slot 1 is `1_item`, and so on. The page previously invented `_itemHash0`, which matches neither the name nor the digit's position.

**`pickedUp`/EWP item-data-unpack addendum (ticket 08, object-ownership.mdx review pass, 2026-09-15)**: initially (wrongly, twice) rejected the maintainer's proposed `filter: int, pickedUp, 1/0` on `ItemDrop` after checking only the base game's own decompile — there, `m_pickedUp` (`ItemDrop.cs:427`) is packed as one bit inside the binary `itemData` byte-array ZDO field (`ItemDrop.cs:1791-1795`, `SaveToZDO`), and the only place a *standalone* `pickedUp` ZDO field exists is `ZDOMan.cs:2189/2214`'s one-time old-save-format migration (`ConvertInventories`), which reads it once then deletes it — so on a live, current-format save there's no bare `pickedUp` field the base game itself exposes. That was true as far as it went, but incomplete: EWP's own `docs/scripting.md` (§"Item data", confirmed directly from EWP's GitHub source) documents that EWP auto-unpacks the packed `itemData` blob and re-exposes `durability`, `stack`, `quality`, `variant`, `crafterID`, `crafterName`, `worldLevel`, and **`pickedUp`** as ordinary scriptable fields — a compatibility layer EWP provides on top of the base game's own packed storage. So `filter: int, pickedUp, 1/0` is real, EWP-native syntax; the maintainer's original example was correct. Also confirmed separately: Valheim's ZDO storage has no distinct "bool bucket" — `ZDO.GetBool()` (`ZDO.cs:683-686`) reads straight from the same int storage `GetInt()` uses, so `filter: int, ...` is the right type for a bool-shaped field regardless. **Lesson for tickets 09-12**: a "not found in the base game's own ZDO writes" result only rules out the *base game* exposing a field directly — always check EWP's own `docs/scripting.md`/source for a compatibility/unpack layer before concluding a proposed field doesn't exist, the same lesson already learned once this session for `prefab:` value-group targeting (see addendum above).

Separately: dropping/tossing an item from an inventory calls `Humanoid.DropItem()` (`Humanoid.cs:859`) → `ItemDrop.DropItem()` (`ItemDrop.cs:1798-1816`), which `Instantiate`s the new dropped-item object on the tossing player's own client — so the tossed item's owner at creation is the tossing player, through the ordinary universal creation-time rule (same mechanism as a builder's building exception), not through any explicit `SetOwner` tied to `pickedUp`. Confirmed no `SetOwner`/`ClaimOwnership` call anywhere references `pickedUp` — it never gates or triggers an ownership change itself, it's purely a discriminator field for telling a tossed item apart from fresh, never-touched loot at the moment each is created.

**Gibber `type: destroy` addendum (ticket 10, object-ownership.mdx review pass, 2026-09-16)**: confirmed `type: destroy` correctly reports the true owner at a Gibber's destruction. Fetched EWP's own `HandleDestroyed.cs` from GitHub — it's a Harmony `prefix` patch on `ZDOMan.HandleDestroyedZDO`, meaning EWP reads the ZDO's live state (owner included) *before* the object is actually removed, not after. Since `Gibber.cs:74-91` (`DestroyAll`) claims ownership and calls `ZNetScene.instance.Destroy(...)` in the same method body — no other destroy call site exists anywhere in `Gibber.cs` — `type: destroy` on `prefab: Gibber` cleanly captures the exact claim-then-delete instant, once confirmed the object is genuinely network-destroyed (not a local-only Unity `Destroy`) and not itself spawned/removed by EWP (which would suppress the trigger per `docs/scripting.md`'s own note). Replaces the page's prior "no clean paste-in script" text.

**TerrainModifier `type: create` addendum (ticket 10, object-ownership.mdx review pass, 2026-09-16)**: confirmed a `TerrainModifier`-carrying object is spawned fresh per edit, not a shared/static object like `_TerrainCompiler`. `TerrainModifier.cs`'s own `OnPlaced()` (line 149) is reached the same way a normal building `Piece`'s placement hook is — gated by the transient static flag `m_triggerOnPlaced`, set only around local piece placement (already noted in this ledger's Table 3 entry for TerrainModifier) — confirming each dig/raise/flatten/paint action places its own small piece-like object carrying this component. So the universal creation-time rule applies directly and cleanly: `type: create` on `prefab: TerrainModifier` reports the real edit-maker. Replaces the page's prior on-demand `_TerrainCompiler` poke-check with this simpler, direct trigger — the poke check wasn't wrong, just more roundabout than necessary once the per-edit creation was confirmed.

**TerrainModifier second spawn path, `Attack.SpawnOnHitTerrain` (ticket 10, object-ownership.mdx review pass, 2026-09-16)**: player digging/raising/flattening/painting isn't the only way a `TerrainModifier`-carrying object gets created. `Attack.cs:1672-1703` (`SpawnOnHitTerrain`, a static method) fires when certain attacks hit terrain — it brackets the spawn with `TerrainModifier.SetTriggerOnPlaced(trigger: true)`, `Instantiate(prefab, ...)`, `TerrainModifier.SetTriggerOnPlaced(trigger: false)`, the exact same `m_triggerOnPlaced` mechanism the TerrainModifier addendum above already confirms for player digging (`Player.cs:3102-3104`) and piece placement. Same ownership rule (universal creation-time rule, owned by whoever's client caused the spawn), just a combat trigger instead of a terrain-tool trigger. Not added to the wiki page's appendix (judged not reproducible enough for a "try it yourself" entry — a reader can't trivially cause a terraforming hit on demand), kept here as a fact for future reference.

**Portal/TeleportWorld scoping decision (ticket 09, object-ownership.mdx review pass, 2026-09-16)**: Portal's own row in Table 1 (`TeleportWorld.cs:SetConnectedPortal`) is real and stays true — but the maintainer decided it's not worth its own appendix entry on the wiki page. The mechanism only ever changes ownership on the *linked partner* portal (and only if that partner is currently ownerless), never on the portal a player actually interacted with — too indirect and rarely-observable to make a clean "try it yourself" entry like every other row on the page. Removed from the live page's appendix; this ledger keeps the finding since it's still true and could matter for a future non-appendix use (e.g. explaining unexpected ownership on a portal nobody touched).

**Ship "first aboard" scenario (ticket 09, object-ownership.mdx review pass, 2026-09-16)**: confirmed the maintainer's framing is accurate as an observed-behavior description, even though the underlying mechanism is the *ordinary* Zone Host proximity rule doing the work, not a Ship-specific "boarding" check. `Ship.cs:683-692` (`UpdateOwner`) only ever reassigns ownership away from the *current* owner when they leave the boat while someone else remains aboard — it says nothing about who becomes owner *first*. In practice, boarding a ship puts a player at minimum possible distance, so the page's own general Zone Host proximity rule (whoever's nearest, rechecked periodically) is what actually hands a freshly-approached, unclaimed ship to the first boarder — Ship's own `UpdateOwner` then keeps that same owner stable while they're aboard, only handing off when they leave with someone else still on it. Two mechanisms working together, correctly described from the outside as one continuous behavior.

**Vagon `attachJoint` addendum (ticket 08, object-ownership.mdx review pass, 2026-09-15)**: Table 1's original row said Vagon has "none dedicated" for a watchable field, since `RPC_RequestOwn` (`Vagon.cs:159-173`) itself sets no field, just `SetOwner(sender)`. Re-checked deeper this pass and found a real, same-shape-as-Container's-`InUse` follow-on: `Interact()` (`Vagon.cs:145-157`) requests ownership if not already owner, then `Update()` (`Vagon.cs:192-214`), gated `if (m_nview.IsOwner())`, processes the pending `m_useRequester` and calls `AttachTo()` (`Vagon.cs:301-334`), which writes `ZDOVars.s_attachJointHash` (`"attachJoint"`, `ZDOVars.cs:43`) to `true` — and `Detach()` (`Vagon.cs:344-362`) writes it back to `false`, also gated `if (m_nview.IsOwner())`. Both directions of the flip are owner-gated, so — same logic as Container's `InUse` — targeting `type: change, attachJoint` reliably reports whoever the current owner actually is, immediately after the real `RPC_RequestOwn` ownership hand-off (not the RPC call's own branch, but the very next tick on the now-owning client). Replaces the page's prior on-demand poke-check for Vagon with a direct trigger. **Lesson for tickets 9-12**: "none dedicated" in Table 1 only means no field is written in the *same branch* as the `SetOwner` call — always check the object's own `Update`/interaction-follow-on methods for an owner-gated field like this one before concluding there's nothing to target directly.

Round 2 caught a sharper mistake underneath that: a "real, correctly-spelled prefab" isn't good enough — it has to be a prefab that actually carries **that row's own Component** (checked one by one against each component's own page on valheimtools.stream, e.g. `valheimtools.stream/wiki/components/Trap`). This caught 7 rows where the named prefab was real but attached to the *wrong* component: `piece_spike_wood` (not a real prefab at all — Trap's real prefabs are `fuling_trap`/`piece_trap_troll`), `piece_hearth` (wrong spelling — the real name is `hearth`), `Saddle`/`SaddleLox` (names the equip *item*, not a prefab carrying the `Sadle` component — the real ones are the 4 rideable creatures `Lox`/`Asksvin`/`Moose`/`Moose_spiritcaller`), `piece_artisantable` (still wrong even corrected to `piece_artisanstation` — neither is ItemStand's real prefab; it's `itemstand`/`itemstandh`), `piece_armorstand` (not a real prefab — was a misread of a localization key; the real ones are `ArmorStand`/`ArmorStand_Female`/`ArmorStand_Male`), `piece_sign` (same localization-key misread — the real prefab is just `sign`), and the mixed Vagon row (`piece_ballista chassis` belongs to Turret not Vagon, `CargoCrate` is a `Container` not a `Vagon` — Vagon's real prefabs are `Cart`/`BatteringRam`/`Catapult`/`Sled`).

Every entry in Table 1 above now carries a bracketed citation stating its source and whether it's confirmed against this repo's own scripts, the decompile, or a component's own valheimtools.stream page. The mechanism-shaped rows (Player.cs hammer-remove, both Fish rows, TerrainModifier, Gibber, StatusEffect base, SE_Demister, TimedDestruction) intentionally keep generic non-committal phrasing ("any non-WNT decoration piece," "fishing minigame fish," "timed-despawn props") rather than naming one specific prefab, since these are internal/cleanup call sites, not a single representative object.
