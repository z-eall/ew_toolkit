[Understanding Triggers](/ew_wiki/ewp/concepts/basic-triggers/) covered `create`, `destroy`, `state`, and `say`. This page covers `realtime` — firing a rule on the real-world wall clock.

<Aside type="note">
Trigger semantics on this page come from EWP's own [`docs/scripting.md`](https://github.com/JereKuusela/valheim-expand_world_prefabs/blob/main/docs/scripting.md), the `type:` bullet.
</Aside>

## Same shape as `time`, different clock, one extra granularity

`type: realtime` fires on the identical schedule shape as [`type: time`](/ew_wiki/ewp/concepts/advanced-triggers-time/) — `<par_0>` the granularity word, each condition value its own par after that — but the clock is the real world instead of Valheim's, in the **server's own timezone**, and it adds a `second` granularity `time` doesn't have (Valheim itself has no in-game seconds; the real world does).

```yaml
- type: realtime, second [unixEpochTimestamp]
- type: realtime, minute [minute] [hour] [dayOfYear]
- type: realtime, hour [hour] [dayOfYear]
- type: realtime, day [dayOfYear]
```

Use `time` for anything that should follow Valheim's own day/night rhythm regardless of server uptime; use `realtime` for anything that should follow the wall clock — a daily reset, a weekday-only event, a real-world countdown.

## Reading the result: `<realtime>` and friends

A `realtime` trigger tells you *that* the clock changed; the `<realtime_X>` functions below tell you *what it says now* — the same trigger-reads-function pairing [`type: time`](/ew_wiki/ewp/concepts/advanced-triggers-time/#time-functions-read-the-clock-this-trigger-reacts-to-it-changing) has with its own Time functions. Three functions cover it:

- **`<realtime>`** — seconds since the Unix epoch (Jan 1, 1970 UTC), as a raw number.
- **`<realtime_X>`** — the clock formatted your way. `X` is a .NET `DateTime` format string, e.g. `<realtime_yyyy-MM-dd HH:mm:ss>` or `<realtime_dddd>` for the weekday name. Uses the **server's** timezone.
- **`<realtime_X_Y>`** — same formatting, but in timezone offset `Y` instead of the server's own — `<realtime_HH:mm_-5>` for Eastern Standard Time, regardless of where the server itself runs.

```yaml
- type: realtime, minute
  command: s It is now <realtime_mm> minutes past <realtime_HH>.

- type: realtime, hour
  command: s It is <realtime_HH_-5> sharp in UTC -5.

- type: realtime, day
  commands:
  - s Date is <realtime_yyyy-MM-dd>.
  - s Today is <realtime_dddd>.
```

<Aside type="caution">
The par mapping for `realtime` (granularity word as `<par_0>`, own unit then the units above it) follows the same pattern as `time`, but `scripting.md` doesn't spell it out for `realtime` specifically — treat it, and day-of-year counting across leap years, as unconfirmed rather than settled fact. Reach for the `<realtime_X>` functions above instead of counting on a specific par index wherever you can.
</Aside>

## Case study - a weekday buff rotation

A simplified weekday buff — a `realtime, day` trigger writes the weekday as a [`globalkey`](/ew_wiki/ewp/concepts/advanced-triggers-no-prefab/#globalkey-reacting-to-a-world-flag-being-set), and a `globalkey` trigger per day reacts to it. `setkey`/`removekey` are ordinary console commands run through the official `command:`/`commands:` fields — vanilla Valheim's own, not EWP's, which is why `scripting.md` doesn't spell out their syntax: `setkey [name]` and `removekey [name]` both take a bare name, no value.

<Steps>

1. **Stamp today's weekday as a global key**

   ```yaml
   - type: realtime, day
     commands:
     - setkey <realtime_dddd>
     - s A new day begins — today is <realtime_dddd>.
   ```

   Every real-world day, this writes today's weekday name (`Monday`, `Tuesday`, ...) as a global key and says so in chat — the message alone is what tells players *anything* changed today, even on a day with no other effect.

2. **Each weekday reacts to its own key, clears yesterday's**

   ```yaml
   - type: globalkey, monday
     commands:
     - removekey sunday
     - setkey EnemyDamage 90
     - s Monday — the fog lifts early, creatures seem sluggish today.

   - type: globalkey, tuesday
     commands:
     - removekey monday
     - removekey EnemyDamage
     - setkey SkillGainRate 200
     - s Tuesday — a restless energy in the air, skills come easier today.

   - type: globalkey, wednesday
     commands:
     - removekey tuesday
     - removekey SkillGainRate
     - setkey ResourceRate 150
     - s Wednesday — the forests feel generous today.

   - type: globalkey, thursday
     commands:
     - removekey wednesday
     - removekey ResourceRate
     - setkey TradeDiscount 20
     - s Thursday — merchants are in a good mood today.

   - type: globalkey, friday
     commands:
     - removekey thursday
     - removekey TradeDiscount
     - setkey EnemyDamage 110
     - s Friday — something restless stirs before the weekend.

   - type: globalkey, saturday
     commands:
     - removekey friday
     - removekey EnemyDamage
     - setkey LootBonus 150
     - s Saturday — the tides carry in more than usual today.

   - type: globalkey, sunday
     commands:
     - removekey saturday
     - removekey LootBonus
     - s Sunday — a calm day, nothing unusual stirring.
   ```

   Every entry does the same three things in order: clear yesterday's weekday flag, clear yesterday's *effect* key (a plain `removekey`, never `removekey KEY VALUE` — that value doesn't belong there, since removing a key doesn't need one), then set today's own effect and say what it is. Sunday sets no effect key at all — a quiet day is a valid day, not every rotation slot needs a mechanical bonus.

</Steps>

## Case study - warning players before an hourly event, not just after

An event that only ever announces itself the instant it starts gives players no chance to be there for it. Layering a few more `minute`-conditioned rules around the same real-world hour turns a silent flip into a countdown players actually notice:

```yaml
- type: realtime, minute 55
  command: s A trader's sail glints on the horizon — the port opens in five minutes.

- type: realtime, minute 59
  command: s The trader's ship turns toward shore — one minute to port.

- type: realtime, minute 0
  commands:
  - s The trading post is open!
  - setkey TradingPostOpen

- type: realtime, minute 1
  commands:
  - s The trading post has closed for the hour.
  - removekey TradingPostOpen
```

Each rule fires once, at one specific minute of every real-world hour — the same `minute [minute]` condition shape from [The four granularities](#same-shape-as-time-different-clock-one-extra-granularity) above, just used four times instead of once. `TradingPostOpen` is a global key other rules can gate on — a real vendor or a lootable chest checking `globalKeys: TradingPostOpen` is what would actually make "open" mean something beyond a message, not shown here.

<Aside type="tip">
This reaches for `minute`, not `second`, on purpose — the page's own caution above already flags `second`'s condition semantics as unconfirmed. `minute [minute]` is the documented, safe way to land a countdown on an exact real-world moment.
</Aside>

## Case study - a real-world daily reset, independent of uptime

`type: time` is tied to Valheim's own in-game day counter, which only advances while the world is actually being played — a server that's offline for real-world days doesn't lose in-game time, but one with light playtime advances its in-game clock slowly. `realtime` follows the wall clock instead, so it's the right choice for anything meant to track the real calendar — a daily reset, a weekend event — rather than how much the world has actually been played.

<Aside type="caution">
Exactly what happens to a `realtime` trigger while the server is offline (fires once to catch up on restart, or is simply missed for that occurrence) isn't documented — don't design a rule that depends on one specific behavior across a restart without testing it first.
</Aside>
