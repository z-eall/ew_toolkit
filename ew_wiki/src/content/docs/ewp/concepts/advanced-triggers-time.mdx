[Understanding Triggers](/ew_toolkit/ew_wiki/ewp/concepts/basic-triggers/) covered `create`, `destroy`, `state`, and `say`. This page covers `time` — firing a rule on **Valheim's own in-game clock**, the one that drives day/night and the calendar day counter inside the world itself. It has nothing to do with your server's real-world wall clock — for that, see the separate [`type: realtime`](/ew_toolkit/ew_wiki/ewp/concepts/advanced-triggers-realtime/) trigger, same shape, different clock.

<Aside type="note">
Trigger semantics on this page come from EWP's own [`docs/scripting.md`](https://github.com/JereKuusela/valheim-expand_world_prefabs/blob/main/docs/scripting.md), the `type:` bullet.
</Aside>

## Works like `change`, but the "field" is the clock

[`type: change`](/ew_toolkit/ew_wiki/ewp/concepts/advanced-triggers-change/) fires when a tracked value changes; `type: time` fires when the clock's value changes — same trigger-and-react shape, just watching a value nobody had to set themselves. Instead of naming a field (`type: change, health`), you name a granularity: `tick`, `minute`, `hour`, or `day`, smallest to largest. Each fires the instant Valheim's own clock rolls that unit over.

`<par_X>` works the same way it does on `change`, too: `<par_0>` is the granularity word itself, and each condition value after it becomes its own par, smallest unit first.

## Time functions read the clock; this trigger reacts to it changing

Don't skip past this because it sounds like a rename of something you already know — the Time functions below and this `time` **trigger** are two halves of the same idea, not two unrelated features that happen to share a word. The trigger decides *when* a rule fires; a function reads *what the clock says* once it has. They're built to be used together — a `type: time, day` rule almost always wants to say what day it is, and the only way to do that is a Time function inside its own `command:`:

```yaml
- type: time, day
  command: s Day <day> dawns.   # <day> reads the in-game day counter the moment this rule fires
```

- `<day>` — whole days since the world started.
- `<time>` — seconds since the world started (`1800` seconds per in-game day).
- `<ticks>` — the same, in ticks. Needs the `long`-variant of a function (`<addlong_X_Y>`, etc.) for any arithmetic on it, not the regular one — see the mod's own [functions.md](https://github.com/JereKuusela/valheim-expand_world_prefabs/blob/main/docs/functions.md) for the full list.
- `<time_X>` — formats game time using a .NET `DateTime` format string, e.g. `<time_yyyy-MM-dd HH:mm:ss>`.

<Aside type="note">
This page's clock has its own separate reading functions from the real-world wall clock — see [`type: realtime`](/ew_toolkit/ew_wiki/ewp/concepts/advanced-triggers-realtime/#reading-the-result-realtime-and-friends) for `<realtime>`/`<realtime_X>`/`<realtime_X_Y>`. Nothing stops a single `command:` from reading both clocks at once, e.g. `s Day <day>, server time is <realtime_HH:mm>`.
</Aside>

### Case study - counting down to a fixed day

`<day>` on its own just answers "which day is it" — the useful move is running it through a Numeric function to answer a real question, like "how many days are left." Here it counts down to a 30-day event, clamped so the message never goes negative once the event ends:

```yaml
- prefab: Player
  type: say, eventdays
  command: s <max_0_<sub_30_<day>>> day(s) left in the event
```

`<sub_30_<day>>` is `30` minus the current day — negative once day 30 passes. `<max_0_X>` (a Numeric function, [covered on Understanding Functions](/ew_toolkit/ew_wiki/ewp/concepts/basic-functions/#kinds-of-functions)) clamps that at `0` instead of letting the message go negative.

## The four granularities

```yaml
- type: time, tick TICKS
- type: time, minute MINUTES HOURS DAYS
- type: time, hour HOURS DAYS
- type: time, day DAYS
```

There's no "second" granularity — Valheim itself has no seconds in-game, only ticks, minutes, hours, and days. Each granularity smaller than `day` also accepts the units *above* it, in that order, so you can pin a rule to one exact recurring moment instead of every occurrence — `hour HOURS DAYS` means "this hour, but only on this day."

### `tick` — fires on every single tick

```yaml
- type: time, tick
  command: s Hello
```

With no condition, this runs on Valheim's fastest, most frequent unit of time — expect it to fire far more often than `minute`. Keep whatever runs here cheap; this is the wrong granularity for anything heavier than a quick check.

### `minute` — a repeating heartbeat

A comma checks several values at once:

```yaml
# Fires when "minute" changes to 0 or 30 — a heartbeat roughly every 30 real-world seconds
- type: time, minute 0,30
  command: s Half-hour mark
```

### `hour` — pinned to one exact moment with the unit above it

`hour`'s shape is `hour HOURS DAYS`, so `<par_1>` is the hour, `<par_2>` the day. A semicolon `;` gives a range:

```yaml
# Only on in-game day 800, fires once for every hour in range 0-23
- type: time, hour 0;23 800
  command: s Hourly check, day 800 only
```

### `day` — every day, or a `*` wildcard pattern

`day` alone (no condition) matches every day. A `*` wildcard picks out days by their last digit:

```yaml
# Fires when the day number ends in 5 — day 5, 15, 25, 35...
- type: time, day *5
  command: s Today is day <par_1>.
```

## Real-world lengths

| In-game unit | Real-world length |
|---|---|
| day | 30 minutes |
| hour | 1.25 minutes (1 min 15 sec) |
| minute | 1.25 seconds |

<Aside type="caution">
`tick` has no reliable real-world length to put in this table — it's tied to the server's own update rate, not a fixed duration, so don't plan exact timing off it. Treat it as "the smallest unit, fires very often" and use `minute` or a `delay:` instead anywhere you need a specific real-world interval.
</Aside>

## Case study - a scheduled bonus, with a clean revert

A resource bonus active every 10th in-game day, back to normal otherwise, using the `*` wildcard together with [`fallback:`](/ew_toolkit/ew_wiki/ewp/concepts/spawn-vs-swap/) so the revert rule only runs when the bonus rule didn't already match:

```yaml
- type: time, day *0   # day 10, 20, 30...
  commands:
  - s Today is a double-yield day!
  - setkey ResourceRate 200   # see the No-Prefab Triggers page for what setkey actually sets

- type: time, day
  fallback: true   # only runs when the entry above didn't already match
  commands:
  - removekey ResourceRate
```

A single exact day instead of a repeating pattern reaches for `value1,value2` or `min;max` on the condition instead of a wildcard — whichever shape actually matches the days you care about.

## Case study - a recurring boss-timer reset

Combine `day` with `hour` to pin a recurring event to the *same in-game moment* every cycle, rather than firing continuously across a whole day. `type: time` has no prefab of its own, and its position always defaults to the world origin `(0,0,0)`, so it can't `spawn:` a boss directly — the real move is to have it `poke:` a marker object already standing in the arena, and let *that* object's own rule do the spawning.

<Aside type="caution">
Pick the marker prefab carefully: it needs to be real (any name typed here has to exist in Valheim) and it needs to do nothing on its own. `guard_stone` looks like an obvious choice for "a marker object standing in the arena," but it's a real structure with a real side effect — it blocks nearby monster spawns — which would fight the very boss spawn this case study is trying to trigger. `piece_banner01` is purely decorative, so it's safe to repurpose as a poke target.
</Aside>

<Steps>

1. **Schedule the reset, guarded against stacking**

   ```yaml
   - type: time, hour 0 5,10,15,20   # hour 0, but only on days 5, 10, 15, or 20
     bannedGlobalKeys: BossArenaActive   # skip the reset if the last boss is still standing
     commands:
     - s A dark presence stirs in the Swamp arena.
     poke:
     - prefab: piece_banner01
       filter: string, Piece.m_name, arenaBossMarker
       position: 320, -140, 0
       parameter: spawnBoss
   ```

   Because `hour` accepts the unit above it (`day`), this fires once per matching day, not once per hour across every day. `bannedGlobalKeys: BossArenaActive` is what makes it a recurring encounter instead of a stacking one — if the last Bonemass isn't dead yet, the scheduled hour skips the reset instead of queuing a second boss on top of it.

2. **Reach the arena, and only the one banner tagged for it**

   ```yaml
   poke:
   - prefab: piece_banner01
     filter: string, Piece.m_name, arenaBossMarker   # matches only the one banner hand-tagged for this arena
     position: 320, -140, 0   # x, z, y — a time trigger's own position always defaults to (0,0,0), so this overrides it to the arena's real coordinates
     parameter: spawnBoss
   ```

   `position:` is what reaches the arena at all — see [Advanced Poke Mechanics](/ew_toolkit/ew_wiki/ewp/concepts/advanced-poke-mechanics/#positionoffset--placing-effects-independent-of-range). `filter:` is what makes it *this* banner: a poke search defaults to a 100m radius and picks whichever match is closest, so without a uniqueness tag, any `piece_banner01` within that range — including a player's own decoration — could get poked instead. Tag the arena's banner when it's placed, with WEC's `data set=` or a build-time `data:` (see [Custom Data: Not Only From a Script](/ew_toolkit/ew_wiki/ewp/concepts/custom-data/#not-only-from-a-script)) — the same pattern used in [World Boss Progression](/ew_toolkit/ew_wiki/ewp/examples/world-progression/#what-it-builds).

3. **The banner answers the poke and spawns the boss**

   ```yaml
   - prefab: piece_banner01
     type: poke, spawnBoss
     spawn:
     - prefab: Bonemass
       data: int, arenaBoss, 1   # flags this specific Bonemass
       triggerRules: true   # spawned objects don't trigger other rules by default — without this, the destroy rule below never fires
     commands:
     - setkey BossArenaActive
   ```

   `setkey BossArenaActive` raises the guard the first rule checks. `data:` tags this one Bonemass so the next rule can tell it apart from any other; `triggerRules: true` is what lets that Bonemass's own death fire a rule at all.

4. **Clear the guard when this Bonemass dies — not any Bonemass**

   ```yaml
   - prefab: Bonemass
     type: destroy
     filter: int, arenaBoss, 1   # only this arena's own Bonemass
     commands:
     - removekey BossArenaActive
   ```

   Without `filter:`, any Bonemass dying anywhere in the world would clear the guard early — a wild one, or a different arena's. With it, only this tagged Bonemass's death resets the timer for the next matching day.

</Steps>

## Case study - tracking day and night as global keys

Valheim's own night doesn't start at an even hour — it begins at the in-game clock's `20:24` (hour 20, minute 24), and day begins at `3:36` (hour 3, minute 36), matching the real-world 21-minute-day/9-minute-night split (see the [Valheim Wiki's Environment page](https://valheim.fandom.com/wiki/Environment) for the full day/night cycle breakdown). `type: time` can turn those two exact moments into global keys any other rule, command, or system can check — not just the rules on this page:

```yaml
- type: time, minute 24;59 20   # any minute from :24 onward, but only during hour 20 (8pm) — the window night can start in
  bannedGlobalKeys: nighttime   # skip every later minute in this window once night is already marked
  commands:
  - s Night falls.
  - removekey daytime
  - setkey nighttime

- type: time, minute 36;59 03   # any minute from :36 onward, but only during hour 3 (3am) — the window day can start in
  bannedGlobalKeys: daytime   # skip every later minute in this window once day is already marked
  commands:
  - s Day breaks.
  - removekey nighttime
  - setkey daytime
```

`minute 24;59` is a range, not one exact minute — it stays open for the rest of hour 20, from `:24` through `:59`. That's a safety window, not a schedule: `type: time, minute` only fires the instant the clock rolls onto a new minute value, so an exact-minute rule (`minute 24 20`) that gets missed once — a laggy tick, a busy server — has no other chance to fire that whole in-game day. The range keeps the rule armed for the rest of the hour instead.

`bannedGlobalKeys:` is what stops that wide window from re-firing on every later minute once the key has already flipped — one flip per transition, no matter how many minutes the window covers.

<Aside type="tip">
If a rule only needs to *behave differently* by day or night — not track the transition itself as something other rules can check — EWP already has a `day:`/`night:` filter field available on any rule, reading Valheim's day/night state directly rather than approximating it from the clock. The global-key pattern above exists for the other case: making "is it night right now" something readable outside of a single rule's own filter.
</Aside>
