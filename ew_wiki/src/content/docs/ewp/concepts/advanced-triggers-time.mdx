[Understanding Triggers](/ew_wiki/ewp/concepts/triggers/) covered `create`, `destroy`, `state`, and `say`. This page covers `time` — firing a rule on **Valheim's own in-game clock**, the one that drives day/night and the calendar day counter inside the world itself. It has nothing to do with your server's real-world wall clock — for that, see the separate [`type: realtime`](/ew_wiki/ewp/concepts/advanced-triggers-realtime/) trigger, same shape, different clock.

<Aside type="note">
Trigger semantics on this page come from EWP's own [`docs/scripting.md`](https://github.com/JereKuusela/valheim-expand_world_prefabs/blob/main/docs/scripting.md), the `type:` bullet.
</Aside>

## Works like `change`, but the "field" is the clock

[`type: change`](/ew_wiki/ewp/concepts/advanced-triggers-change/) fires when a tracked value changes; `type: time` fires when the clock's value changes — same trigger-and-react shape, just watching a value nobody had to set themselves. Instead of naming a field (`type: change, health`), you name a granularity: `tick`, `minute`, `hour`, or `day`, smallest to largest. Each fires the instant Valheim's own clock rolls that unit over.

`<par_X>` works the same way it does on `change`, too: `<par_0>` is the granularity word itself, and each condition value after it becomes its own par, smallest unit first.

## Time functions read the clock; this trigger reacts to it changing

Don't skip past this because it sounds like a rename of something you already know — [Time functions](/ew_wiki/ewp/concepts/advanced-functions/#time-functions) (`<day>`, `<realtime_X>`, and friends) and this `time` **trigger** are two halves of the same idea, not two unrelated features that happen to share a word. The trigger decides *when* a rule fires; a function reads *what the clock says* once it has. They're built to be used together — a `type: time, day` rule almost always wants to say what day it is, and the only way to do that is a Time function inside its own `command:`:

```yaml
- type: time, day
  command: s Day <day> dawns.   # <day> reads the in-game day counter the moment this rule fires
```

## The four granularities

```yaml
- type: time, tick TICKS
- type: time, minute MINUTES HOURS DAYS
- type: time, hour HOURS DAYS
- type: time, day DAYS
```

There's no "second" granularity — Valheim itself has no seconds in-game, only ticks, minutes, hours, and days. Each granularity smaller than `day` also accepts the units *above* it, in that order, so you can pin a rule to one exact recurring moment instead of every occurrence — `hour HOURS DAYS` means "this hour, but only on this day."

### `tick` — fires on every single tick

```yaml
- type: time, tick
  command: s Hello
```

With no condition, this runs on Valheim's fastest, most frequent unit of time — expect it to fire far more often than `minute`. Keep whatever runs here cheap; this is the wrong granularity for anything heavier than a quick check.

### `minute` — a repeating heartbeat

A comma checks several values at once:

```yaml
# Fires when "minute" changes to 0 or 30 — a heartbeat roughly every 30 real-world seconds
- type: time, minute 0,30
  command: s Half-hour mark
```

### `hour` — pinned to one exact moment with the unit above it

`hour`'s shape is `hour HOURS DAYS`, so `<par_1>` is the hour, `<par_2>` the day. A semicolon `;` gives a range:

```yaml
# Only on in-game day 800, fires once for every hour in range 0-23
- type: time, hour 0;23 800
  command: s Hourly check, day 800 only
```

### `day` — every day, or a `*` wildcard pattern

`day` alone (no condition) matches every day. A `*` wildcard picks out days by their last digit:

```yaml
# Fires when the day number ends in 5 — day 5, 15, 25, 35...
- type: time, day *5
  command: s Today is day <par_1>.
```

## Real-world lengths

| In-game unit | Real-world length |
|---|---|
| day | 30 minutes |
| hour | 1.25 minutes (1 min 15 sec) |
| minute | 1.25 seconds |

<Aside type="caution">
`tick` has no reliable real-world length to put in this table — it's tied to the server's own update rate, not a fixed duration, so don't plan exact timing off it. Treat it as "the smallest unit, fires very often" and use `minute` or a `delay:` instead anywhere you need a specific real-world interval.
</Aside>

## Case study - a scheduled bonus, with a clean revert

A resource bonus active every 10th in-game day, back to normal otherwise, using the `*` wildcard together with [`fallback:`](/ew_wiki/ewp/concepts/spawn-vs-swap/) so the revert rule only runs when the bonus rule didn't already match:

```yaml
- type: time, day *0   # day 10, 20, 30...
  commands:
  - s Today is a double-yield day!
  - setkey ResourceRate 200   # see the No-Prefab Triggers page for what setkey actually sets

- type: time, day
  fallback: true   # only runs when the entry above didn't already match
  commands:
  - removekey ResourceRate
```

A single exact day instead of a repeating pattern reaches for `value1,value2` or `min;max` on the condition instead of a wildcard — whichever shape actually matches the days you care about.

## Case study - a recurring boss-timer reset

Combine `day` with `hour` to pin a recurring event to the *same in-game moment* every cycle, rather than firing continuously across a whole day. `type: time` has no prefab of its own, and its position always defaults to the world origin `(0,0,0)`, so it can't `spawn:` a boss directly — the real move is to have it `poke:` a marker object already standing in the arena, and let *that* object's own rule do the spawning:

```yaml
- type: time, hour 0 5,10,15,20   # hour 0, but only on days 5, 10, 15, or 20
  bannedGlobalKeys: BossArenaActive   # skip the reset if the last boss is still standing
  commands:
  - s A dark presence stirs in the Swamp arena.
  poke:
  - prefab: piece_banner01   # a real, purely decorative banner piece — placed once in the arena, its only job here is to give this poke something to reach
    position: 320, -140, 0   # x, z, y — a time trigger's own position always defaults to (0,0,0), so this overrides it to the arena's real coordinates
    limit: 1   # if more than one piece_banner01 happens to stand within range, only poke one — otherwise every one of them spawns its own boss
    parameter: spawnBoss

- prefab: piece_banner01
  type: poke, spawnBoss
  commands:
  - setkey BossArenaActive
  spawn:
  - prefab: Bonemass
    data: int, arenaBoss, 1   # flags this specific Bonemass, so the destroy rule below reacts only to it
    triggerRules: true   # spawned objects don't trigger other rules by default — without this, the destroy rule below never fires

- prefab: Bonemass
  type: destroy
  filter: int, arenaBoss, 1   # only this arena's own Bonemass — a wild Bonemass dying elsewhere must not clear the guard
  commands:
  - removekey BossArenaActive   # clears the guard so the next matching day can respawn it
```

Because `hour` accepts the unit above it (`day`), the first rule fires once per matching day rather than once per hour across every day. `bannedGlobalKeys: BossArenaActive` is what makes this a real recurring encounter instead of a stacking one: if players haven't killed the last Bonemass yet, the scheduled hour skips the reset instead of queuing up a second boss on top of it. `position:` on the poke is what overrides a time trigger's always-zero default position to reach the arena's real coordinates instead — see [Advanced Poke Mechanics](/ew_wiki/ewp/concepts/advanced-poke-mechanics/#positionoffset--placing-effects-independent-of-range).

Three easy-to-miss requirements make this actually work as one boss, not several, and make the last rule fire at all: `limit: 1` on the poke, because a plain `piece_banner01` match has no idea which banner is "the" arena marker — without a limit, every banner within range gets poked, and every poke spawns its own boss; `triggerRules: true` on the spawn, because EWP's own docs are explicit that objects spawned or removed by the mod don't trigger `create`/`destroy` rules unless this is set; and `filter: int, arenaBoss, 1` on the destroy rule, because without it *any* Bonemass dying anywhere in the world — not just this arena's — would clear the guard early. The `data:` on the spawn is what makes that filter possible: it tags this one Bonemass so the destroy rule can tell it apart from every other.

<Aside type="caution">
Pick the marker prefab carefully: it needs to be real (any name typed here has to exist in Valheim) and it needs to do nothing on its own. `guard_stone` looks like an obvious choice for "a marker object standing in the arena," but it's a real structure with a real side effect — it blocks nearby monster spawns — which would fight the very boss spawn this case study is trying to trigger. `piece_banner01` is purely decorative, so it's safe to repurpose as a poke target.
</Aside>

## Case study - tracking day and night as global keys

Valheim's own night doesn't start at an even hour — it begins at the in-game clock's `20:24` (hour 20, minute 24), and day begins at `3:36` (hour 3, minute 36), both confirmed against the real-world 21-minute-day/9-minute-night split on the [Valheim Wiki's Environment page](https://valheim.fandom.com/wiki/Environment). `type: time` can turn those two exact moments into global keys any other rule, command, or system can check — not just the rules on this page:

```yaml
- type: time, minute 24;59 20   # any minute from :24 onward, but only during hour 20 (8pm) — the window night can start in
  bannedGlobalKeys: nighttime   # skip every later minute in this window once night is already marked
  commands:
  - s Night falls.
  - removekey daytime
  - setkey nighttime

- type: time, minute 36;59 03   # any minute from :36 onward, but only during hour 3 (3am) — the window day can start in
  bannedGlobalKeys: daytime   # skip every later minute in this window once day is already marked
  commands:
  - s Day breaks.
  - removekey nighttime
  - setkey daytime
```

`minute 24;59` is a range, not one exact minute — it stays open for the rest of hour 20, from `:24` through `:59`. That's a safety window, not a schedule: `type: time, minute` only fires the instant the clock rolls onto a new minute value, so an exact-minute rule (`minute 24 20`) that gets missed once — a laggy tick, a busy server — has no other chance to fire that whole in-game day. The range keeps the rule armed for the rest of the hour instead, and `bannedGlobalKeys:` is what stops it from re-firing on every one of those later minutes once the key has already flipped — wide window for reliability, single flip per transition.

<Aside type="tip">
If a rule only needs to *behave differently* by day or night — not track the transition itself as something other rules can check — EWP already has a `day:`/`night:` filter field available on any rule, reading Valheim's day/night state directly rather than approximating it from the clock. The global-key pattern above exists for the other case: making "is it night right now" something readable outside of a single rule's own filter.
</Aside>
