**Poke** sends a message from one rule to another — it's how one object tells another "do something now." Every [rule](/ew_toolkit/ew_wiki/ewp/concepts/start-scripting/) so far reacted only to its own trigger (`create`, `destroy`, `say`, ...). Poke lets one rule trigger another rule directly, instead of waiting for the game to trigger it.

## The minimal poke

One rule sends a poke, another rule reacts to it:

<Steps>

1. **Send the poke**

   ```yaml
   - prefab: Player
     type: say, open
     poke:
     - prefab: wood_door
       parameter: openDoor  # the name that links this poke to its receiver
   ```

   When **Player** says "open" in chat, this rule pokes every `wood_door` in range, passing `openDoor` along as the parameter.

2. **React to the poke**

   ```yaml
   - prefab: wood_door
     type: poke, openDoor  # only answers a poke sent with this exact parameter
     data: int, state, 1
   ```

   `type: poke, openDoor` fires only when `wood_door` receives a poke whose parameter is exactly `openDoor` — then this rule applies `int, state, 1` to it (opens the door).

</Steps>

Both rules live in the same script — see [A script can hold more than one rule](/ew_toolkit/ew_wiki/ewp/concepts/start-scripting/#a-script-can-hold-more-than-one-rule).

## The parameter is just a name

The parameter is what links a poke to its receiver — any word or number works, but a descriptive name (`openDoor`, not `1` or `hello`) keeps a script with multiple pokes readable.

<Aside type="caution">
The two sides have to match — a typo or a renamed parameter on one side breaks the connection silently. Matching itself ignores capitalization (`openDoor` and `opendoor` still connect), so it's a real spelling difference that breaks it, not the letter case. See [When a poke doesn't fire](#when-a-poke-doesnt-fire) below.
</Aside>

## Narrowing who gets poked: `filter:`

[`filter:`](/ew_toolkit/ew_wiki/ewp/concepts/basic-filter/) works under `poke:` the same way it does anywhere else — it doesn't set anything, it only checks a condition, and only pokes the objects that already pass:

```yaml
poke:
- prefab: wood_door
  filter: int, isWoodDoor, 1  # only pokes doors where isWoodDoor already equals 1
  parameter: openDoor
```

<Aside type="tip">
An older script might use `data:` here instead of `filter:` — that's a **legacy alias**, doing the exact same filtering job under a name that's easy to confuse with a real data-apply. Swap it to `filter:` if you copied it from an old script:

```yaml
poke:
- prefab: wood_door
  data: int, isWoodDoor, 1  # legacy alias for filter: — still works, same check
  parameter: openDoor
```
</Aside>

## When a poke doesn't fire

A poke that doesn't work almost never throws an error — it just goes quiet.

<Aside type="caution">
Don't do this: no error, no warning — a broken poke just silently does nothing. Four common causes below, each shown broken next to its fix.
</Aside>

**1. Bad indentation on the list item** — a `poke:` list follows the [same shape as `spawn:`](/ew_toolkit/ew_wiki/ewp/concepts/start-scripting/#a-rule-can-do-more-than-set-data); indenting the second field too far breaks the item:

```yaml
# WRONG — parameter is indented past prefab, so it isn't read as part of this list item
poke:
- prefab: wood_door
    parameter: openDoor
```

```yaml
# CORRECT — both fields align
poke:
- prefab: wood_door
  parameter: openDoor
```

**2. Missing hyphen** — without the `-`, YAML reads this as a single map, not a list of one item, and the whole rule fails to parse as a poke:

```yaml
# WRONG — no hyphen, so this isn't a list item at all
poke:
  prefab: wood_door
  parameter: openDoor
```

```yaml
# CORRECT
poke:
- prefab: wood_door
  parameter: openDoor
  delay: 1  # optional: seconds to wait before poking
```

**3. Misspelled parameter name** — matching ignores capitalization, but any other difference breaks it:

```yaml
# Calling rule sends the parameter "openDoor"
- prefab: Player
  type: say, open
  poke:
  - prefab: wood_door
    parameter: openDoor

# Receiving rule listens for "openDor" — one letter short, never matches
- prefab: wood_door
  type: poke, openDor
  data: int, state, 1
```

Fix: spell the parameter identically on both sides. (`openDoor` and `OPENDOOR` would still connect — only a real spelling difference like the typo above breaks it.)

**4. No receiver at all** — a poke with nothing listening for it fires into empty air:

```yaml
# Sends a poke with parameter "openDoor"...
- prefab: Player
  type: say, open
  poke:
  - prefab: wood_door
    parameter: openDoor

# ...but no rule anywhere has `type: poke, openDoor` to catch it
```

Fix: add a `type: poke, openDoor` rule somewhere in the script.

If a poke chain isn't working, checking that every `parameter:` name is spelled identically on both sides catches the most common case first.

<Aside type="note">
Poke has more fields beyond what's shown here — `delay:`, `repeat:`, `limit:`, `maxDistance:`, and others control timing, repetition, and range. This page covers the connection mechanic itself, not every field poke accepts. (Note `objects:` entries have their own, separately-scoped `maxDistance:` too — see [Filter: by Objects](/ew_toolkit/ew_wiki/ewp/concepts/objects-filtering/) — same field name, different job.) For the rest of poke's field set, and reusable patterns built from it — self-poking, delayed resets, filter-gated counters — see [Advanced Poke - Mechanics](/ew_toolkit/ew_wiki/ewp/concepts/advanced-poke-mechanics/) and [Advanced Poke - Creative Systems](/ew_toolkit/ew_wiki/ewp/concepts/advanced-poke-creative-systems/).
</Aside>

<Aside type="tip">
To message a client directly instead of poking another object, see [Understanding RPC](/ew_toolkit/ew_wiki/ewp/concepts/basic-rpcs/).
</Aside>
