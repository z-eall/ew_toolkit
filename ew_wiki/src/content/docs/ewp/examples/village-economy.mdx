This page ports a real, live server's village-progression script — two separate `.yaml` files that turned out to share one saved number between them. One system locks and unlocks crafting stations (and feasts) as the server progresses; a completely separate system delivers cargo shipments to villages, using a `weight:` computed from a real-time counter instead of a fixed number. They read like two unrelated mechanics — until you notice both of them check the exact same saved key to decide how far the server has come.

<Aside type="note">
The *mechanism* is what's being taught here, not a guarantee that every field name below is bug-free. Admin-debug scaffolding, commented-out test blocks, and a few unverified fields were trimmed out — see the note at the bottom for exactly what and why.
</Aside>

## One counter, three systems

The whole thing hangs off a single [EWP key](/ew_wiki/ewp/concepts/ewp-key/): `bfvworldlevel`, a plain number (0 upward) standing in for "how far this server has progressed." An admin sets it by hand from chat:

<Steps>

1. **The admin command**

   ```yaml
   - prefab: Player
     type: say, !wlvl 0;999
     admin: true
     cancel: true
     exec: <save_bfvworldlevel_<max_0_<par_1>>>
   ```

   `admin: true` restricts this to admins; `cancel: true` stops the chat message itself from showing (it's a command, not something meant to be read as regular chat). `<max_0_<par_1>>` clamps whatever number the admin typed to never go below 0 — `<par_1>` is the number itself, `0;999` in the trigger just tells EWP which range of chat words to match. `exec:` runs the `<save_*>` function purely for its side effect, same as [Custom Data: EWP Key](/ew_wiki/ewp/concepts/ewp-key/) covers.

2. **Everything else reacts to it changing**

   `type: key, <name>` fires whenever a saved key's value actually changes — not on every read, only on a real change:

   ```yaml
   - type: key, bfvworldlevel
     poke:
     - prefab: CraftingStation, StationExtension
       filters:
       - int, isBfvVillageStation, 1
       - int, isBfvVillageStationExt, 1
       filterLimit: 1
       maxDistance: 20000
       parameter: findUnsealedVillageStation
     - prefab: dvergrprops_crate
       filters:
       - int, isBfvVillageStationSeal, 1
       - int, isBfvVillageStationSealExt, 1
       filterLimit: 1
       maxDistance: 20000
       parameter: findSealedVillageStation
   ```

   `prefab: CraftingStation, StationExtension` doesn't name one specific object — those are Component names, and [`prefab:` accepts a component as a value group](https://github.com/JereKuusela/valheim-expand_world_prefabs/blob/main/docs/scripting.md), matching *every* object that has that Component. So this one rule reaches every crafting station and every station extension on the whole map in one poke, no matter what they're each individually called. `filters:`/`filterLimit: 1` (see [Advanced Filter: Plurals](/ew_wiki/ewp/concepts/advanced-filter-plural/)) then narrows that flood down to just the ones already flagged as unsealed or sealed, so this rule can re-check every station's lock state the instant the world level changes — without knowing any of their names in advance.

</Steps>

## Crafting stations that lock themselves

Each station tier — Workbench, Forge, Cauldron, and so on — has its own required world level. Rather than write one rule per station name, the script stores that requirement as data, keyed off the station's own prefab id:

```yaml
- value: requiredWorldLevel_piece_workbench, 0
- value: requiredWorldLevel_piece_workbench_ext1, 0

- value: displayName_piece_workbench, Workbench
- value: displayName_piece_workbench_ext1, Chopping Block
```

`<prefab>` is a [function](/ew_wiki/ewp/concepts/basic-functions/) that returns the calling object's own prefab id — combine it into another function's name, and `<requiredWorldLevel_<prefab>>` resolves to "look up the value entry named `requiredWorldLevel_` plus whatever this exact object is called." One rule, run against every station, reads a different answer for each one:

```yaml
- prefab: CraftingStation, StationExtension
  type: poke, findUnsealedVillageStation
  poke:
  - self: true
    parameter: sealIfWorldLevelValid <ge_<load_bfvworldlevel=0>_<requiredWorldLevel_<prefab>>>
```

`<ge_X_Y>` (see [Understanding Functions](/ew_wiki/ewp/concepts/basic-functions/)) returns `true`/`false` for "is the current world level greater than or equal to this station's requirement" — that result becomes the next poke's own parameter, [self-poked](/ew_wiki/ewp/concepts/basic-poke/) right back onto the same station:

```yaml
- prefab: CraftingStation
  type: poke, sealIfWorldLevelValid false
  swap:
  - prefab: dvergrprops_crate
    data: isBfvVillageStationSeal
```

`type: poke, sealIfWorldLevelValid false` only matches when that parameter actually came out `false` — the world level isn't high enough yet. [`swap:`](/ew_wiki/ewp/concepts/spawn-vs-swap/) replaces the whole station with a `dvergrprops_crate` (a dwarven storage crate), carrying a `data:` entry that locks it down:

```yaml
- name: isBfvVillageStationSeal
  ints:
  - isBfvVillageStationSeal, 1
  - WearNTear.m_noSupportWear, 0
  - Piece.m_canBeRemoved, 0
  floats:
  - WearNTear.m_health, -1
  strings:
  - sealedPrefab, <prefab>
```

`WearNTear.m_health, -1` makes the crate unbreakable, `Piece.m_canBeRemoved, 0` stops it being picked back up by hand, and `WearNTear.m_noSupportWear, 0` means it never needs a wall or floor under it to stay standing. The interesting line is the last one: `sealedPrefab, <prefab>` runs at swap time, while the object being swapped is still the *original* station — so `<prefab>` captures the station's own id (`piece_workbench`, say) and saves it as a string, right there on the crate that's about to replace it.

That's what makes the reverse direction trivial. When the world level rises again, the same fan-out poke reaches sealed crates instead, and this rule swaps the crate back — reading the id it saved on itself instead of needing a separate lookup table for "what was this crate before it was sealed":

```yaml
- prefab: dvergrprops_crate
  type: poke, unsealIfWorldLevelValid true
  filter: int, isBfvVillageStationSeal, 1
  swap:
  - prefab: <string_sealedPrefab>
    data: isBfvVillageStation
```

<Aside type="tip">
`<prefab>` saved into the *new* object's own data, then read back off that same object later, is a reusable pattern any time a swap needs to remember what it replaced — it doesn't need a second `value:` table matched by hand, the object just carries its own history.
</Aside>

The real script repeats this pattern for six station tiers (Workbench through Black Forge) — this page only worked through Workbench in detail, since that's the one whose value names line up exactly with the confirmed prefab ids ([`piece_workbench`](https://valheim-modding.github.io/Jotunn/data/prefabs/prefab-list.html), [`piece_workbench_ext1`](https://valheim-modding.github.io/Jotunn/data/prefabs/prefab-list.html)); the same `<requiredWorldLevel_<prefab>>` mechanism carries the rest, just with more `value:` entries.

## Feast tables upgrade the same way

The same world level also swaps a base camp's Feast piece for a tougher one as the server progresses — `swap: prefab: <campFeastWorldLevel<par_2>>` picks a Feast variant (`FeastMeadows`, `FeastBlackforest`, and so on — all [confirmed real prefabs](https://valheim-modding.github.io/Jotunn/data/prefabs/prefab-list.html)) out of another `value:` table keyed by world level number instead of by prefab id, with a plain [`fallback: true`](/ew_wiki/ewp/examples/basic-rng/) rule underneath in case the level is higher than any table entry covers. Same lookup-table idea as the stations, just keyed differently — nothing new to teach here.

## Cargo shipments: a weight built from a live counter

The second file runs on its own independent schedule — it delivers cargo shipments to villages, using [`type: realtime`](/ew_wiki/ewp/concepts/advanced-triggers-realtime/) (real-world clock time, not in-game time) so the counter keeps climbing even with nobody online:

```yaml
- type: realtime, hour
  exec: <save++_cargospawnfactor>
```

Every real-world hour, `<save++_X>` bumps a counter by 1 (see [Custom Data: EWP Key](/ew_wiki/ewp/concepts/ewp-key/)). Nothing spawns yet — this rule only counts. The spawn attempt is a separate rule watching that same counter through a `type: key` range:

```yaml
- type: key, cargospawnfactor 4;9999
  weight: <sub_<ceil_<mul_<par_1>_0.33>>_1>
  exec: <save_cargospawnfactor_0>
  poke:
  - prefab: rug_bogwitch_wolf
    filters:
    - int, villageCargoTent, 1;<randomVillageLvl<load_bfvworldlevel=0>>
    - int, villageCargoReceived, 0
    limit: 1
    parameter: findEmptyCargoSpawner <randomCargoLvl<load_bfvworldlevel=0>>
```

This is the main thing worth taking away from this whole page: `weight:` doesn't have to be a fixed number. [Weight and Chance](/ew_wiki/ewp/examples/basic-rng/) only showed constants, but a weight can just as well be the result of a function, recomputed fresh every time the rule is checked — here, built from `<par_1>`, the current counter value itself (see [Understanding Pars](/ew_wiki/ewp/concepts/basic-pars/)).

<Aside type="caution">
This is described as a 33% / 66% / 100% ramp as the counter climbs through 4, 5, 6 real hours, but that exact curve can't be independently re-derived from `weight:`'s documented pool math — probability depends on every other rule sharing the same weight pool at match time, which isn't fully knowable from the docs alone. Treat the specific percentages as unconfirmed; the technique itself — computing a weight from a live value instead of hardcoding it, plus the reset below — is what's solid here.
</Aside>

`exec: <save_cargospawnfactor_0>` resets the counter back to 0 the moment a shipment does go out, so the whole climb starts over — a self-resetting real-world timer, built entirely out of fields [Adding Randomness](/ew_wiki/ewp/examples/basic-rng/) already introduced.

### Where the world level comes back in

The poke above reads `<randomVillageLvl<load_bfvworldlevel=0>>` and `<randomCargoLvl<load_bfvworldlevel=0>>` — two more `value:` tables, this time keyed by the *same* `bfvworldlevel` the station section reads. This is the actual seam joining the two files: a low world level narrows which villages are even eligible for a delivery and shrinks how much cargo they can receive; a high one opens up the whole map and raises the ceiling. Nothing about the cargo timer above needed to know that detail — it just asked "how many villages, how much cargo" and let the shared counter answer.

### An existing prefab, repurposed as a marker

`rug_bogwitch_wolf` is a real, ordinary decorative rug prefab — not a custom object built for this script. The script plants one per village and gives it two custom flags that mean something only in this script's own context:

```yaml
- prefab: rug_bogwitch_wolf
  type: poke, findEmptyCargoSpawner
  data: int, villageCargoReceived, 1
  spawn:
  - prefab: MyVillageCargoItem
    pos: 0,0,0.5
```

`villageCargoTent` (which village this rug stands for) and `villageCargoReceived` (whether that village's last delivery is still sitting there, uncollected) exist only because this rule set them — the rug component itself never heard of either one. Any harmless, easy-to-place decorative prefab works the same way: a free, invisible-in-plain-sight marker object, carrying whatever custom state a script wants to track per location.

<Aside type="caution">
The real script spawns `Cargo<par_1>` — a range of custom cargo-crate items from another mod bundled into that server, not vanilla Valheim or anything in Jotunn's prefab list. This page uses the placeholder `MyVillageCargoItem` above instead of presenting that name as a confirmed prefab — swap in a real, verified lootable prefab of your own.
</Aside>

### Telling a player what's available

The live script also answers a chat command with each village's delivery status, using [`objectRpc:`](/ew_wiki/ewp/concepts/basic-rpcs/) with the `Message` RPC to pop the result on screen, and a self-poking countdown to keep checking one village at a time before printing — the exact same loop-with-`weight: 1e30`-terminal-case pattern [Advanced Poke - Creative Systems](/ew_wiki/ewp/concepts/advanced-poke-creative-systems/#a-self-closing-timer-carried-entirely-in-the-poke-itself) already covers in full. Nothing new to teach there either — this script is just a second real example of that same pattern, not a different one.

## What got cut, and why

<Aside type="note">
Trimmed for this page, and left out rather than guessed at:
- Admin-debug chat commands and commented-out test blocks from both files — scaffolding, not the mechanism itself.
- The full six-tier station table (Forge through Black Forge) and the fifteen-village status message — same pattern repeated many times over; one worked example teaches the mechanism without the repetition.
- The `MarketPlaceNPC` "pay the cargo master" interaction — that prefab isn't in Jotunn's list or valheim.wiki, meaning it comes from a separate NPC mod. Left out entirely rather than taught as if confirmed.
- `HoverText.m_text` and a handful of other Component fields on the sealed-crate data entries (`StaticPhysics.m_pushUp`, `DropOnDestroyed.m_spawnYOffset`, and similar) — plausible, but unconfirmed, so they're not included in the `isBfvVillageStationSeal` entry shown above.
</Aside>
