# EWP Toolkit — Map

## Destination

A public, cost-free, self-updating web app ("EWP Toolkit") where a scripter opens one EWP YAML file or a batch of files and gets structural validation (bad keys, wrong types, spelling — flagged with exact file/line location) plus key/type autocomplete, each file checked independently. It runs on a JSON Schema built fresh from Jere's EWP source, regenerated and redeployed automatically by a scheduled GitHub Action, so it stays paired with EWP updates with no manual work. The schema/validation logic is architected as a reusable package so a VS Code extension is a cheap follow-on later (not part of this map).

Reaching the destination means: a scripter can hit a public URL, load one file or a batch, and get accurate structural errors plus autocomplete, with zero ongoing manual maintenance to keep pace with Jere's updates.

- **Standing rule (added ticket 13 round 8, broadened by the [Schema Source Audit map](../schema-source-audit/map.md)):** before hand-encoding *any* strict/rejecting validation rule from docs prose — an enum's casing, a field-name completeness list (`additionalProperties: false`), a requiredness condition, an array-vs-scalar/nested-shape assumption — check it against EWP/WEC's actual current C# source (or get a live in-game test) rather than trusting the docs' description as the full accepted grammar. Docs show the idiomatic form, not necessarily the whole accepted grammar. This has now caught real gaps twice from casing alone (ticket 13 rounds 8, and `filter`/`bannedFilter` in ticket 08) and three more from field-completeness/shape (Schema Source Audit: missing `delay`, `spawn`/`swap`'s legacy scalar form, `itemEntry.customData`'s real object shape) — treat it as a real, recurring failure mode of docs-derived schema work, not a one-off.
- **Standing message-quality checklist (hub-wide — applies to every tool this hub ever hosts, not just `ewp_validator`; added post-Schema-Source-Audit).** Before shipping any user-facing diagnosis/error/warning message:
  1. **Name the offending value or key**, not just its location — `'nonsense' is not a valid type` beats `/type pattern mismatch`.
  2. **Say what to do next**, not just what's wrong — a message that only states the problem still leaves a non-coder stuck.
  3. **No raw schema/regex/parser jargon** in user-facing text — no bracket-class regexes, no `instancePath`/`additionalProperties`-speak, no raw third-party library error codes or messages shown bare. If a message is generated (schema validator, YAML parser, any future library), it gets a translation layer before it reaches the user — see `structuralPrecheck.ts`'s ajv `pattern`-keyword override and `yamlErrorMessages.ts`'s 23-code translator for the pattern to follow.
  4. **One diagnosis per root cause.** Before adding a new check, ask whether an existing check already flags the same mistake from a different angle (e.g. an invalid `type:` word shouldn't also trip a separate "missing prefab" error) — see `structuralPrecheck.ts`'s `KNOWN_TYPES`-gated `checkPrefabRequiredness` for the suppression pattern, and the RPC/format-lint/comment-out suppressions already built into the same file for others.
  5. **A closed, enumerable upstream error set (a `type`/`code` union, not free-text) gets a complete translation table, not a "handle the common ones" subset** — a fixed-size union is cheap to cover exhaustively and a partial table just defers the same work to the next person who hits an unmapped code. Free-text upstream errors (no closed code) instead get a generic-but-friendly wrapper, never shown raw.
  6. Every message-quality fix gets a regression test, same as any other bug fix — a wording rewrite has no other guardrail against silently drifting back to the raw/technical version.
  7. **If an existing UI control directly resolves this exact diagnosis, name it in the message text** (e.g. "use the 'Clear invalid files' trash icon to remove it") — appended prose, not a separate inline button/element. This only applies per-message, not per-category: a category can mix messages that have a one-click fix with ones that don't (e.g. "Legacy but working" covers both a rename-fixable filename notice and non-UI-fixable legacy-syntax notices), so check each message's own fix path rather than assuming the whole category shares one. **Name the control in plain words only — never an emoji or icon glyph** (added 2026-08-19, [ticket 19](issues/19-icon-symbol-consistency-standing-rule.md)): diagnosis message text renders through `escapeHtml()` because it can carry scripter-typed content, a real XSS boundary that rules out embedding live markup, so a symbol placed there can never actually match the real UI control — it can only ever be decoration that drifts. Say what the button looks like or is labeled ("the trash icon", "the 'Clear invalid files' button"), never draw it.
  8. **Share visual identity across Tools, don't copy it** (added 2026-08-19, [ticket 19](issues/19-icon-symbol-consistency-standing-rule.md)/[ticket 20](issues/20-shared-icon-token-module.md)): icon paths and the identity color palette (background/panel/border/text/muted/hover) live in the shared `shared/` module, imported by every Tool and the Landing page — never hand-copied between them. A copied icon or color drifts the moment one copy changes and the other doesn't; this already happened once (`ewp_validator`'s icon set was a manual copy of `nav.ts`'s, and the two `style.css` files' `--info` variable silently came to mean two different colors). Severity/diagnostic colors (error/warning/info) are the one exception — those are validator-only semantics, not Hub identity, and stay local to whichever Tool defines them.
  9. **A confirm-style modal's primary/default button must be explicitly chosen and stated per use case, never assumed from a generic OK/Cancel convention** (added 2026-08-19, [validator-round2 ticket 09](../validator-round2/issues/09-custom-confirm-modal.md)): state which action is primary and why (safety default vs. task-completion default) in the resolution. The default lean is the non-destructive/safe choice as primary (Cancel on a delete/overwrite confirm) — a task-completion action only earns primary when it's itself the safe choice (e.g. "Skip these files" on the upload-gate confirm, which avoids adding structurally-invalid files by default). Pairs with a keyboard rule: a destructive confirm gets no Enter-key default at all (only Escape → cancel), so a stray keypress can never trigger data loss; only a genuinely non-destructive confirm may wire Enter to its primary button.
- **Standing rule — two-step check before adding any new validation/diagnosis rule (hub-wide; added 2026-08-19, ties together the two rules above):**
  1. **Source-verify first** (the ticket 13 round 8 rule, above): confirm what the new rule should actually check/reject against EWP/WEC's current C# source or a live in-game test, not just docs prose.
  2. **Then check it against the existing rule set for duplication/clash** (message-quality checklist item 4, above): would this new rule ever fire on the same root cause an existing check already flags, from a different angle? "The existing rule set" means the current code — `schema/generate.mjs` + `structuralPrecheck.ts`/`formatLint.ts`/`referenceValidation.ts`/`rpcValidation.ts` — not a separate registry or log to build and maintain.
  This order matters: running the duplication check *first* invites guessing ("these two rules sound like they could overlap") before the new rule's real trigger condition is even pinned down. Source-verifying first turns step 2 into a check against a **proven** trigger condition, so a suspected clash gets confirmed or ruled out on fact rather than guesswork — same as how the Round 10 duplicate/clash fix in [ticket 13](issues/13-v1-user-testing-feedback.md) only became fixable once the `type`/`types` case-insensitivity rule's real behavior (source-verified in round 8) was known precisely enough to tell a genuine "type is invalid" case apart from a genuine "type is valid but missing its prefab" case.
- **Standing rule — `data.yaml`-relevant checks source-verify against whichever mod's source actually implements the behavior, not a blanket "both repos" requirement (added 2026-08-19, corrected same day after [research/wec-ewp-correlation.md](research/wec-ewp-correlation.md)):** EWP and WEC (https://github.com/JereKuusela/valheim-world_edit_commands) are **fully independent mods with zero code coupling** — no assembly reference, no `BepInDependency` on each other, not even a shared helper library between them (WEC's own YAML utility comes from a third mod, `ServerDevcommands`, that EWP doesn't depend on). What looks like "WEC owns `data.yaml`, EWP references it" is really **two separate implementations of the same author's shared folder convention**: EWP's `FileLoading.cs` and WEC's `DataLoading.cs` each independently scan the identical `data` subfolder path/glob/case-rule into their own separate in-memory registry. So the check isn't "always consult both" — it's **consult whichever mod's `Awake()`/`Start()` actually wires up the loading or command logic for the specific YAML shape in question**: EWP's source alone is authoritative for how EWP decides which files it loads (confirmed sufficient for [validator-round2 ticket 08](../validator-round2/issues/08-data-filename-folder-rule.md)'s folder-loading rule — WEC's independent loader corroborates but adds nothing new); WEC's source alone is authoritative for the shape of a WEC data entry itself (already used this way in [ticket 07](issues/07-wec-entry-key-discrepancy.md)); EWP-only features (Custom saved keys) have no WEC equivalent at all, so checking WEC there finds nothing (confirmed in [validator-round2 ticket 07](../validator-round2/issues/07-custom-key-validation-rework.md)'s research). Extends the source-verify-first rule above rather than replacing it — this only corrects which repo(s) count as "the source" per rule.

## Decisions so far

- [Reframe: is EW Toolkit a single tool or a multi-tool site?](issues/15-multi-tool-site-reframe.md) — Widen the *vision* (a site hosting tools for Jere's Valheim mods, EWP validator = tool #1) but NOT this map: this map freezes at the standalone validator, the umbrella name `ew_toolkit` is adopted now, and the multi-tool hub becomes its own new map charted after the validator ships. Umbrella scope tiered (Jere's mods now; general Valheim world-editing only-if-required later); name branded after the ExpandWorld flagship line.
- [Set up GitHub account and EWP Toolkit repo](issues/01-github-setup.md) — Repo created at https://github.com/z-eall/ewp_toolkit; local folder renamed to `ewp_toolkit` to match; remote wired, not yet pushed.
- [What's the technical shape of a Monaco-based validator on GitHub Pages + Actions?](issues/05-web-app-mechanics.md) — Confirmed $0-forever. Vite as bundler (monaco-yaml requires one), schema bundled at build time, single combined `schedule`-triggered workflow (regen + build + deploy) — a two-workflow split would silently break since `GITHUB_TOKEN` can't chain workflows. Full findings: [research/05-web-app-mechanics.md](research/05-web-app-mechanics.md).
- [Can key references be validated without full data-aware game data?](issues/04-reference-validation-feasibility.md) — Yes for `data.yaml` named templates (clean definition/usage pair, same-file and cross-file, no game data needed) — the concrete v1 feature. Custom saved keys are a weaker best-effort warning. Prefab names, global keys, and event names must wait. Full findings: [research/04-reference-validation-feasibility.md](research/04-reference-validation-feasibility.md).
- [Can EWP schema generation support multiple mod versions?](issues/03-multi-version-feasibility.md) — Ship latest-only for v1. No GitHub tags/releases exist; `publish/manifest.json`'s commit history gives a reliable ~30-version history instead, and the schema does change meaningfully across versions, so version-picker is a well-scoped ~1-2 day fast-follow once v1 is stable, not a v1 requirement. Full findings: [research/03-multi-version-feasibility.md](research/03-multi-version-feasibility.md).
- [How is EWP's YAML structure documented/derivable from Jere's repo?](issues/02-schema-source.md) — Docs + C# source together get most of the way, but a real residual gap exists: core YAML deserialization/coercion logic lives in a closed-source shared library, so at least one discrepancy (`filter`/`bannedFilter`) can't be settled from public material. Top level is a discriminator-less array needing a `oneOf` union; ~70 fields are C#-typed as string but semantically bool/number/enum with a function-syntax escape hatch; requiredness is conditional on `type`, not flat. Full findings: [research/02-schema-source.md](research/02-schema-source.md).
- [Resolve the `data:`/`name:` entry-key discrepancy in WEC's data system](issues/07-wec-entry-key-discrepancy.md) — Definitively resolved via source: `name:` is the only valid key for a WEC data entry's name property; `data:` is a copy-paste typo confined to one section of WEC's README, not a real alias — following it silently drops the entry. Schema accepts only `name:`, optionally lint-flags `data:` in that position. Full findings: [research/07-wec-entry-key-discrepancy.md](research/07-wec-entry-key-discrepancy.md).
- [Scope the data.yaml reference-validation feature for v1](issues/06-reference-validation-scope.md) — Undefined `data:` reference is a hard error; dead `data.yaml` entry is a low-severity info hint; custom-saved-key mismatch ships in v1 as a warning that points the user at `ewp_data.yaml` to verify before treating it as a real bug, rather than being deferred outright.
- [Decide policy for schema gaps where source/docs disagree or are closed-source](issues/08-gap-handling-policy.md) — `filter`/`bannedFilter` singular forms confirmed valid via live in-game testing (scalar shorthand for the plural list) — corrects ticket 02's "unresolvable" framing. `component.m_field`-style data keys validate as unconstrained strings, not a pattern (WEC's `data set=` command allows arbitrary custom key names too). Two `paint` enums scoped per-location. Deprecation follows Jere's own `docs/legacy.md`, no invented opinions.
- [Decide type-validation strategy given ~70 nullable-string C# fields with documented semantic types](issues/09-type-validation-strategy.md) — Enum fields (`type`, `paint`) validate strictly against the known list; bool/number-with-alt-syntax fields (`chance`, `admin`, etc.) accept the native type or an unconstrained string, no narrow function-only pattern. Conditional requiredness scoped to just `prefab`-required-per-`type`, modeled as a warning (mirrors EWP's own runtime severity) — no full per-type field-relevance matrix for v1.
- [Prototype the top-level oneOf union for EWP/WEC's discriminator-less array](issues/10-discriminatorless-array-prototype.md) — Confirmed naive `oneOf` produces unusable errors (13-15 raw Ajv errors dumped across all branches for one typo or a total mismatch). Real implementation uses a structural pre-check (guess intended shape by distinguishing keys, then validate against only that schema) — `oneOf`/`anyOf` stays the acceptance mechanism, not the error-reporting source. Prototype: [`prototype/oneof-union-error-quality`](https://github.com/z-eall/ewp_toolkit/tree/prototype/oneof-union-error-quality).
- [Prototype the validator page's UI/UX](issues/11-validator-ui-prototype.md) — Chosen layout: sidebar file list with per-file error badges + main editor + a bottom Problems panel listing every error across all loaded files at once. Most directly serves the multi-file correlated-system debugging pain point driving this whole map. Prototype (3 variants compared): [`prototype/validator-ui-layout`](https://github.com/z-eall/ewp_toolkit/tree/prototype/validator-ui-layout).
- [Decide repo structure/scaffold and initial bootstrapping](issues/12-repo-scaffold.md) — Layout: `.github/workflows/`, `schema/generate.mjs`, `src/` with a gitignored generated schema, one root `package.json`. MIT license and a minimal README added. Pages source setting flipped to "GitHub Actions" — done.
