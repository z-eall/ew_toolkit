## Question

Rework `ew_wiki`'s page chrome to fix 3 reported problems, all living in `Header.astro`/`CollapsibleToc.astro` (built in tickets 08/09):

1. **Title crop** — the site title (`SiteTitle`/`.title-wrapper`) renders with weird cropped-off lines on the left, which visibly displaces the sidebar's page list and the search box too.
2. **Broken floating buttons** — the "on this page" / "back to top" icon-rail buttons (`CollapsibleToc.astro`) are out of shape, mispositioned, and have overlapping/colliding click targets.
3. **Remove the right panel** — once the floating buttons work, the right-hand TOC panel they open is redundant. Remove it entirely from every page and reclaim that width for content — the floating rail already covers "jump to a heading" and "back to top."

These three are bundled into one ticket: #3 changes what the floating rail even opens into (there's no side panel left to anchor to, so #2's redesign can't be finalized before #3's removal is decided), and #1's crop may share a root cause with the same header/sidebar grid #2/#3 sit inside.

**Maintainer's explicit instruction: don't patch.** A CSS nudge that hides the symptom without understanding *why* the title crops or *why* the buttons collide repeats the exact "narrow verification" failure pattern `ai-workflow-audit` Round 2 diagnosed. Diagnose the real cause first (likely something in Starlight's own header/sidebar grid interacting with the ticket-08/09 overrides), redesign, then verify on a real running page — not source-only.

**Related but separate**: the hub-wide site-nav bar's own shape mismatch on this page is being fixed on the [Hub map](../ew_toolkit/hub-map.md)'s new [nav-bar-unification ticket](../ew_toolkit/issues/21-unify-hub-tool-nav-bar.md), not here — that ticket is the top strip; this ticket is the title/search/TOC area below it.

## Answer

All 3 root causes diagnosed live (not guessed) via the browser: DOM inspection, computed-style reads, and real click tests against the built `dist/` output, then fixed and re-verified the same way.

**1. Title crop — real cause: `--sl-nav-height` never grew to match the added nav-bar row.** Starlight wraps this whole Header override in its own fixed `<header class="header">` landmark, sized by `height: var(--sl-nav-height)`. That variable is also what every other part of the page (sidebar, TOC, content) uses to reserve top clearance so nothing renders under the fixed header. Ticket 08 added the site-nav row on top of Starlight's own title/search row without updating it — so the landmark rendered taller than the space reserved for it, and the sidebar started underneath/overlapping it. That's what looked like "cropped": the title wasn't clipped, it was covered.

  Fixed in `Header.astro`'s script: measures the landmark's real natural content height and writes it into `--sl-nav-height`. Naively reading the landmark's own rendered height is circular (its height *is* that variable, so reading it back just returns the stale value) — sidestepped by temporarily forcing `height: auto` (inline style wins over the stylesheet's `var()` rule), reading `scrollHeight`, then restoring. Re-measures via `ResizeObserver` on the landmark's *children* (not the landmark itself, which would self-trigger) — catches the nav row wrapping to 2 lines on narrow viewports, verified at 375px.

**2. Right panel — real cause: a full sidebar-width column reserved for a 34px icon rail.** `ew_wiki/src/styles/theme.css` already had a comment from ticket 09 noting the rail "floats in a wide empty gap" and worked around it by widening the *content* column instead — a mitigation, not a fix. The reserved right-hand column (`.right-sidebar-container`, Starlight's own `[data-has-toc] .main-pane` width formula) was a full `--sl-sidebar-width` (~300px at desktop width) for a rail that only ever needs ~34px. Shrunk both paired formulas to a new `--ewp-toc-rail-width` (3.5rem) instead of `--sl-sidebar-width`; content now uses the reclaimed space. Verified: `main-pane` width grew from 785px → 1029px at 1400px viewport width; landing/validator pages (untouched by this file) confirmed unaffected.

  Shrinking that column surfaced a real second-order bug: the popup panel (13.5rem, deliberately wider than the column so it opens *over* content) started rendering with 0 width — Starlight's `.right-sidebar { overflow-y: auto }` implicitly forces `overflow-x: auto` too (per the CSS overflow spec's visible-paired-with-non-visible rule), which now clips anything wider than the column. Fixed with `overflow: visible` on `.right-sidebar` — safe here since the popup has no long content of its own that needed that scrollbar.

**3. Floating buttons "not in position, collision way off" — real cause: two independently-positioned elements landing 0.4px apart.** The header's search button and the TOC rail are positioned by two unrelated pieces of Starlight/CollapsibleToc CSS that happen to both target the same top-right corner; the search button's rendered height slightly overhangs its own header row, closing what should have been headroom for the rail down to under half a pixel — read as touching, not just close. Fixed by adding real clearance (`padding-top: calc(var(--sl-nav-height) + 0.75rem)` on `.right-sidebar`, layered on top of the dynamic nav-height fix from #1, not replacing it) — verified gap went from 0.375px to 12.375px.

**Not changed**: `CollapsibleToc.astro`'s own component code (rail markup, toggle/scroll-spy/back-to-top behavior) — every bug traced back to the *surrounding* Starlight layout (`--sl-nav-height`, the reserved column, the overflow rule), not the rail's own implementation, which worked correctly once its environment did.

**Verified**: full combined hub rebuilt via WSL after each fix; checked live in the browser at 3 viewport widths (375px mobile, 800px, 1400px desktop) — title renders cleanly with no overlap, sidebar/search fully readable, floating rail sits with clear spacing below search, popup panel opens fully visible over the reclaimed content width, and the landing/validator pages (which don't load this file) are unaffected.

## Round 2 (reopened 2026-09-12)

The maintainer caught 3 real problems the first pass missed — this ticket's own "verified at 3 widths" claim above wasn't enough; live re-inspection each time is what actually caught these:

1. **Nav bar didn't reach the page edges, header wasn't compact.** Real cause: `header.header` (Starlight's own fixed landmark) still carries its own `--sl-nav-pad-x` horizontal padding, sized for its single original title/search row. Our shared nav bar (`site-nav`) was injected as a sibling *inside* that same padded landmark, so it inherited a ~24px inset on both sides that no other Tool's nav bar has. Fixed by stripping the landmark's own `padding-inline` and re-applying it only to the inner title/search wrapper (`header.header > div.header`), so just that row keeps its inset and the nav row goes edge-to-edge.

   The "not compact" half wasn't a bug to fix, it's a real Starlight constraint: the maintainer's own comparison was to `ewp_validator`, which is a single plain-scrolling page with nothing `position: fixed`, so its own second header row (`.app-header`) just flows normally underneath the sticky nav at whatever height it needs. Starlight's page architecture is different — the header has to be `position: fixed` for the sidebar/TOC/content geometry to work at all (confirmed reading `PageFrame.astro`/`TwoColumnContent.astro`: `--sl-nav-height` is load-bearing for the sidebar popover's `inset-block-start` and the main content's `padding-top`, not just cosmetic). Un-fixing it to match validator's simplicity would mean reimplementing large parts of Starlight's own layout system — a bigger redesign than "imitate what's already there" actually calls for once the real constraint is visible. Two stacked rows in a fixed header stays the shape; only the padding bug above was real.

2. **Content still didn't reclaim the right column's width, and the floating rail rendered off past the right edge of the page.** Two more distinct math bugs (not the cascade/layer issue they first looked like — a plain `<style>` override, then the same override with `!important`, both empirically lost to Starlight's own `@layer starlight.core` rule live in the browser for reasons not fully run to ground; switched to setting these via direct inline style in `Header.astro`'s existing script instead, which reliably wins over any external stylesheet rule that isn't itself `!important`):
   - `.main-pane`'s `100%` is already net of the *left* sidebar (Starlight reserves that room via `padding-inline-start` on an ancestor, `.main-frame`, not via a flex sibling's width) — subtracting `--sl-sidebar-width` again double-counted it. Fixed: just `100%`, matching what Starlight itself gives a page with a left sidebar and no TOC.
   - `.right-sidebar`'s `width: auto` doesn't shrink-wrap to the visible icon rail — it shrink-to-fits the *whole* element's content, including mobile-only TOC markup that's only visually hidden (not `display: none`) at desktop widths, and a third Starlight rule (`PageSidebar.astro`'s `.sl-container`, sized from `--sl-sidebar-width` too) right-aligns the rail inside a box that stayed ~268px wide regardless of how narrow `.right-sidebar` itself was set — pushing the rail out past the page's real right edge once the outer column shrank. Fixed: explicit `4.5rem` width on `.right-sidebar` (room for the 34px buttons plus Starlight's own padding) and `width: auto` on `.sl-container` so it stops forcing that stale sidebar-width-derived box.

**Verified (round 2)**: rebuilt via WSL after each fix, checked live at 1200px and 1400px desktop widths — nav bar flush to both edges, content fills the full reclaimed width, floating rail renders inside the visible page and its popup opens overlapping content (not blocking clicks on the text underneath, confirmed via `elementFromPoint`). **Not yet re-verified at mobile width (375px)** — a real, separate layout problem was spotted there during this pass (header grows to ~248px because the nav bar wraps across 4 lines, plus a mobile menu-toggle button visually overlapping nav text) that predates this ticket and wasn't part of the maintainer's original report; flagged, not fixed, pending a decision on whether it's in scope here or its own ticket.

## Round 3 (same day, 2026-09-12) — the real reason round 2 still looked broken live

The maintainer opened the live browser pane themselves and reported round 2 was "even worse" — off-center content, stray border lines, and the floating button still misbehaving. Root cause: **the app's default browser-pane width (~800-860px) sits below Starlight's own 1152px (`72rem`) breakpoint**, and every round-2 fix (`.main-pane`, `.right-sidebar-container`, `.right-sidebar` sizing, the rail's floating position) only took effect *above* that breakpoint. All of round 2 was verified at 1200px/1400px — widths the maintainer's own view never actually was. Two distinct problems, both traced to that same gap:

1. **A second, completely separate stock component was showing, never touched by any of this ticket's work.** `PageSidebar.astro` (Starlight's own, confirmed by reading its source) renders *two* independent TOC UIs into the DOM at once — the icon rail (wired in as `TableOfContents`, everything ticket 23 has been fixing) above 1152px, and a totally different, unmodified "mobile" dropdown pill (`MobileTableOfContents`) below it — swapped via CSS visibility classes, not a real conditional render. Below 1152px the maintainer was looking at stock Starlight the entire time, which is why nothing ever looked fixed. Overridden `PageSidebar` with a version that renders only the rail, unconditionally — one floating-button design at every width, not two components silently swapping under the maintainer's feet.
2. **The rail's floating (`position: fixed`) behavior was itself gated behind the same 1152px media query** in Starlight's own CSS, so once the stock mobile pill was removed, the rail rendered but sat in normal document flow (pushing content down) instead of floating over it, below that width — read as "content off-center / weird border lines" because `.right-sidebar` also still carried Starlight's own `border-inline-start`, invisible above 1152px (that whole rule is inside the same gated block) but rendering as a stray vertical line once the rail was visible-but-unfixed below it. Fixed by setting `position: fixed`, `top`, `z-index`, and `border-inline-start: none` directly via the same inline-style mechanism already used for width — unconditional, not media-gated.

**Verified (round 3)**: rebuilt via WSL, checked live at the browser pane's actual default width (~860px, not a custom-resized one) — same icon rail as desktop, no stock mobile pill, floats fixed over content on toggle with no stray border, popup opens without pushing or hiding anything. New files: `ew_wiki/src/components/PageSidebar.astro`. Edited: `ew_wiki/astro.config.mjs` (new `PageSidebar` override), `ew_wiki/src/components/Header.astro` (unconditional rail positioning). **Still not checked at true mobile width (375px)** — same pre-existing, separate header-wrap issue from round 2 remains unaddressed.

2. Move search into the floating icon rail as a magnifier button, above the page-navigation button — clicking it opens an expanded search box to its **left**.
3. The page-navigation ("on this page") button opens its list to its **left** too, not below.
4. Fix the content column, which was rendering hard against the right edge instead of centered — margins to be reported if the cause wasn't obvious, for the maintainer to judge.

**Implementation:**

- `Header.astro` no longer imports or renders `SiteTitle`/`Search` at all — it renders only the shared nav bar (`<Fragment set:html={navHtml} />`), nothing else. Starlight's fixed header landmark now wraps exactly one real child, same as every other Tool.
- `header.header`'s own padding (`ew_wiki/src/styles/theme.css`) is now stripped entirely (`padding: 0`, was previously only `padding-inline: 0` with `padding-inline` handed back to the now-deleted title-row wrapper) — with no second row left, there's nothing left to reserve it for.
- `.site-nav`'s `line-height` is now pinned explicitly to `normal` in `shared/theme.css` (not ew_wiki-locally) — found live: Starlight sets a global `line-height: 1.75` on its own pages that the plain landing/validator pages don't have, which alone made the byte-identical shared nav bar render ~5.6px taller on the wiki than the other 2 Tools even with identical padding. A shared component silently depending on its host page's own typography was the real bug; fixed at its one source, not patched locally.
- `CollapsibleToc.astro` rebuilt: each rail button (search, on-this-page, back-to-top) now sits in its own `position: relative` wrapper, and each one's panel is `position: absolute; top: 0; right: calc(100% + 0.5rem)` — anchored to open flush left of *that specific* button, top-aligned with it, regardless of how many other buttons are stacked above or below.

Instead, this drives Pagefind's own raw JS API directly (`ew_wiki/pagefind/pagefind.js`, the same index Starlight's own build step already generates) — lazy-loaded on first open, not on every page load. Real search, not a placeholder: confirmed live by typing "field" and getting 8 real ranked results including the current page, each linking to its real URL.

Starlight's own `TwoColumnContent.astro` sets `--sl-content-margin-inline: auto 0` on `.main-pane` specifically for its *real*-reserved-TOC-column case, snugging content against that column instead of centering it in the wider space. That variable was still being set and still applying even though round 3 already removed the actual reserved column — a stale side effect of a design that no longer exists, not a real left/right choice anyone was making. Reset to plain `auto` (centers).

## Round 5 (same day, 2026-09-12) — content width, and a real scroll-bleed bug

Two follow-ups from the maintainer after round 4 landed.

**1. Content column widened further.** With the right TOC column no longer reserved (round 3), `--sl-content-width: 56rem` was leaving real, visible empty space on both sides — the maintainer asked to go wider. First attempt (64rem) overshot: forgot `ContentPanel.astro`'s own 24px inline padding also eats into the space available, so 64rem actually landed at only ~6.5px margin each side — too tight, found by measuring before shipping it, not after. Settled on **60rem**, which accounts for that padding: at 1400px wide, content is now 960px (was 896px) with **38.5px margin each side** (was 70.5px) — real breathing room, well short of edge-to-edge.

**2. Scroll bleed — a real bug, not user error.** The maintainer described exactly the right symptom: aiming to scroll the search box or the sidebar and having the page (or the other one) move instead, especially with rapid hovering/spam-scrolling between them. Root cause: the floating search/TOC panels only made their *inner results list* independently scrollable (`overflow-y: auto` on `.ewp-search-results` alone) — so scrolling anywhere else in the panel (the input box, empty space, a short list with nothing to scroll) had no local scroll target, and the wheel event fell straight through to whatever was underneath. Separately, the left sidebar (Starlight's own `.sidebar-pane`) scrolls independently but has no `overscroll-behavior`, so once you scrolled it to its own top/bottom, the browser's native "scroll chaining" handed the rest of that scroll motion to the page behind it.

Fixed both the same way: made the *whole panel* (not just its list) a real scroll container (`overflow-y: auto` directly on `.ewp-search-panel`/`.ewp-toc-panel`, with a `max-height` cap) and added `overscroll-behavior: contain` to it and to the sidebar, so a maxed-out inner scroll stops there instead of leaking to whatever's behind it.

**Verified with real scroll simulation, not just CSS inspection:** used the browser tool's own scroll gesture (not a synthetic JS event, which some engines don't scroll-chain the same way as real input) at a point over the search panel — `window.scrollY` stayed 0 before and after. Scrolled well past the sidebar's own bottom (30 wheel-ticks against a 315px scroll range) — sidebar's `scrollTop` stopped exactly at its max (315), `window.scrollY` stayed 0 throughout. Scrolling over plain page content still scrolls the page normally (confirmed `scrollY` 0 → 500 after a 5-tick scroll there). All three checked in the same session, same page, so the fix and the regression check used the same real numbers.

## Round 7 (same day, 2026-09-12) — the theme toggle really was rendering differently, but not from different code

The maintainer pushed back hard on round 6's "confirmed pixel-identical" close-out: the theme-toggle button visibly uses a colorful emoji on `ew_wiki` and a plain outline symbol on landing/`ewp_validator`. Checked directly rather than assumed: `outerHTML` of the button on all 3 pages is byte-identical (`<button id="..." class="theme-toggle" aria-label="Current theme, click to switch">☾ Dark</button>`) - genuinely the same shared markup from `shared/navBar.ts`/`shared/theme.ts`, not a hand-copy. So the maintainer's observation and "same shared code" were both true at once, because the real cause was neither: `shared/theme.css`'s `.theme-toggle` rule had `font-family: inherit`. Landing/validator's own pages set a plain sans-serif stack with no emoji fonts in it; `ew_wiki`'s host page (Starlight) sets its own global stack that lists `"Apple Color Emoji"`/`"Segoe UI Emoji"`/`"Noto Color Emoji"` ahead of any plain glyph for the ☾/☀ characters - so the *exact same character* gets drawn by a different font depending only on which page the shared button happens to be dropped into.

This is the identical shape of bug as round 4's line-height fix on the same `.site-nav` rule (a shared component silently inheriting a host-page property instead of pinning its own) - should have been caught then, by generalizing "check every property this component doesn't explicitly set" rather than stopping once the one bug found that round was fixed. Fixed the same way: `font-family` pinned explicitly on `.site-nav` itself (not just `.theme-toggle`), so every child - the toggle, the changelog link, the nav links - is covered against this drifting again, not just the one button that happened to get reported.

**Verified (round 7)**: rebuilt via WSL. `getComputedStyle` on both `.site-nav` and `.theme-toggle` now reports the identical plain stack (`-apple-system, "Segoe UI", Roboto, sans-serif`) on `ew_wiki` as on landing/validator - confirmed live, not just read from source. Screenshot confirms the button now renders as a plain outline crescent, not a colored emoji. Edited: `shared/theme.css` (`font-family` moved from a per-button `inherit` to an explicit pin on `.site-nav` as a whole).

## Round 7.5 (same day, 2026-09-12) — the maintainer's "check the other 2 pages" catch caught a real regression

Maintainer asked to check landing and validator too before moving on, rather than trusting round 7's close-out. That check found a real bug the round-7 fix had introduced: `getComputedStyle(theme-toggle-button).fontFamily` on landing came back `Arial`, not the pinned stack - the button wasn't picking up `.site-nav`'s explicit `font-family` pin at all on that one page.

**Real cause**: `<button>` (and every other form control - `input`, `select`, `textarea`) never inherits `font-family` from its ancestors by default. This is a plain browser rule, not specific to this bar - a button only picks up an ancestor's font if something explicitly says `font-family: inherit` (or restates the value) on the button itself. Round 7 removed the per-button `inherit` from `.theme-toggle` and moved the declaration up to `.site-nav`, assuming normal inheritance would carry it down - but `.site-nav` is a `<div>`, not a form control, so normal inheritance rules apply to it; the button one level down is where inheritance silently stops. Round 7's own verification only checked `ew_wiki`, where Starlight's own base CSS happens to reset `button { font: inherit }` globally, and `ewp_validator` has its own local `button, input, ... { font-family: inherit }` reset in its `style.css` - both masked the gap by accident. Landing has neither reset, so its button fell back to the browser's plain UA default (`Arial`) instead of the pinned stack the whole time round 7 was "verified."

**Fixed**: `font-family: inherit;` restored directly on `.theme-toggle` in `shared/theme.css` - now explicit on the one element type (a form control) that actually needs it stated, regardless of whether the host page happens to carry its own button reset.

**Verified (round 7.5)**: rebuilt via WSL, restarted the preview server, re-read live. `getComputedStyle(button).fontFamily` now reports the identical pinned stack on all 3 pages (landing, validator, `ew_wiki`) and nav height is 53px on all 3. Zero console errors on any of the 3 pages. Landing's toggle button screenshot confirmed showing plain "☾ Dark" text, not Arial's own rendering of it (visually indistinguishable in this case, but now for the *pinned* reason, not an accidental one). Edited: `shared/theme.css` (`.theme-toggle` regains an explicit `font-family: inherit`, on top of - not instead of - `.site-nav`'s own pin, since form controls need the explicit restatement that other elements don't).
