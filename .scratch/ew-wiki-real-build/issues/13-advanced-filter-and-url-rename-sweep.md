**Fourth follow-up (same session) — the real build didn't match the mockup, root cause + fix.** Maintainer compared the shipped widget against the prototype and flagged several regressions: the stale-note warning icon was missing, checklist/PASS-FAIL coloring wasn't showing at all, the PASS/FAIL icon sat above the text instead of beside it, checklist rows looked squeezed with misaligned checkboxes, the two columns weren't the same height, and asked to drop "Show the math" (redundant with the plain-English line) and quote the button name in the stale-note wording.

Diagnosed live rather than guessed: inspected computed styles in the actual dev-server page. Found the coloring loss was a real bug, not a CSS mistake — the client script set `summaryBox.className = 'fl-summary-box fl-fail'` wholesale, which wipes the Astro-injected scoping class that element needs for any of this component's own scoped CSS rules to match it at all (confirmed via computed style: the class was gone, `--fl-fail` fell through silently, `color`/`border-left-color` both resolved to the inherited base text color instead). The checklist `<li>`/`<label>` rows have the same problem structurally, but worse — they're created fresh via `document.createElement`, so they *never* carry a scoping class to begin with. Fixed by (a) switching the summary box to `classList.add/remove` instead of overwriting `className` (preserves the scope class), and (b) marking the two checklist color rules `:global(...)` (matching the pattern already used for the injected icon SVGs, which is exactly why *those* worked correctly the first time). The stacked-icon bug was a separate, smaller issue: raw `<svg>` computed to `display:block` in this browser once sized, so icon+text wrapped onto separate lines — fixed by making `.fl-verdict` a flex row.

Also fixed in the same pass: checklist rows now `align-items: flex-start` (was `center`, which misaligned the checkbox against multi-line banned-item text), stale-note icon is server-rendered directly in the Astro template (`set:html`) rather than injected by the client script — sidesteps the whole scoping question since it's static content — wording now reads `click "Check" to update the list below`, and both columns are pinned to a shared fixed height (230px) with their own internal scroll instead of growing with a long paste or a long checklist. "Show the math" removed entirely (markup, CSS, and the now-dead `mathEl` JS). Re-verified live against the dev server after a full stop/restart: color, layout, stale-note, and light/dark theme all confirmed working via both computed-style inspection and screenshots.

**Fifth follow-up (same session) — fixed 2x2 layout, and a second real alignment bug.** Maintainer still wasn't happy with the two-column free-flowing layout: asked for a strict 4-zone grid instead (top-left input / top-right list sharing one height, bottom-left button / bottom-right result sharing another, a center dividing line between left and right), and — separately — for the box to never resize under any circumstance, with space pre-reserved for every variable bit of text (the stale note, checklist entries, the result sentence).

Rebuilt the markup as a single CSS Grid (`grid-template-columns: 1fr 1fr; grid-template-rows: 150px 84px`) so the "match size" requirement is structural, not a coincidence of content: cells sharing a grid row are the same height by construction. Added a `::before` pseudo-element as the single center divider line spanning both rows. Every cell scrolls its own overflow (`overflow-y: auto`) instead of the grid ever growing. The stale note switched from `display: none/flex` to `visibility: hidden/visible` so its line height stays reserved at all times — confirmed live that ticking/typing never shifts the Check button.

Found a second real bug while fixing the "list items are misaligned, and get worse after ticking" complaint: the checklist row was a flex row where the icon only existed in the markup when a condition was ticked (unticked rows had no icon element at all) — so ticking a box didn't just recolor the row, it also inserted an icon that pushed the text rightward, meaning ticked and unticked rows never shared a left edge. Fixed by giving every row a fixed three-column grid (`16px checkbox / 16px icon-slot / 1fr text`) where the icon slot always exists as an empty span and is only filled with markup when matched — so the text column start position is identical regardless of state. Verified live: ticked and unticked rows share the same left edge, and toggling a checkbox no longer shifts anything.

**Seventh follow-up (same session) — a real scrollbar-height mismatch bug, root-caused via direct measurement instead of guessed.** Maintainer asked for the exact numeric value controlling the vertical gap between checklist rows (so they could specify the new number directly rather than describing "too loose"/"too tight") — answered directly from computed styles (`.fl-row`'s `padding: 1px 0`, i.e. 2px total between adjacent rows) rather than estimating, then set it to `0` on request.

Separately, the maintainer flagged that the left (input) and right (checklist) boxes' scrollbars sat at different heights, even though both cells are in the same 150px grid row. Rather than guess at a CSS fix, measured the actual DOM rects live. Found two distinct stray-margin bugs, neither written anywhere in this component's own CSS — both traceable to Starlight's own base styles leaking onto plain elements this component uses:
1. `.fl-cell-list`'s own box had a `margin-top: 16px` nobody in this file set, so even after both cells hit height:150px, the list cell's box still floated 16px below the textarea's.
2. Every `<label class="fl-row">` checklist row had `margin-bottom: 20px` — labels get default bottom margin in Starlight's form-field spacing — which was the actual (and only) source of the "space between rows" the maintainer was asking about; `.fl-row`'s own `padding` was a red herring that had already been reduced correctly.

Fixed by zeroing `margin` explicitly on `.fl-cell` (all four cells) and on `.fl-checklist :global(.fl-row)` (the dynamically-created label needs `:global` for the same scoping reason as the other dynamic rules). Verified via direct rect measurement after each fix, not just visual inspection: row-to-row gap is exactly `0`, and the two boxes' top/bottom edges now match to the pixel (`Math.abs(diff) < 0.5`, confirmed via JS in the live page).
